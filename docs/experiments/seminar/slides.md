## 01. 설비 중단과 대체 배정 판단

<!-- chapter:연구 방향과 업무 의미 -->
**“설비 M02가 멈췄습니다. 주문 O17과 O18을 M03으로 돌려도 되나요?”**

{{story:question}}

> 지금 연구에서 온톨로지와 SHACL의 가장 설득력 있는 역할은 LLM의 지능을 높이는 것보다 여러 구성요소가 같은 의미로 데이터를 읽고 판단하도록 만드는 것입니다.

<!-- notes -->
답변 정확도만 보면 온톨로지와 SHACL이 만드는 가치의 일부를 놓칠 수 있다. 공장 사례에서 M02가 멈추고 M03의 자격 갱신 소식이 들릴 때 현장 담당자는 대체 배정 가능 여부를 묻고 품질 담당자는 자격의 제품·기간 범위를 확인하며 감사 담당자는 판단 근거와 규칙 버전을 기록하려 한다. 다만 온톨로지와 SHACL은 구분해야 한다. 온톨로지는 무엇을 어떤 관계로 표현하고 해석할지 다루며 SHACL은 그 데이터가 특정 용도의 조건을 만족하는지를 다룬다. 둘 중 하나만 쓰는 설계도 가능하다.

## 03. 데이터 구조에 업무 의미 남기기

> 공장 사례에서 `M03 → Q03R`이라는 연결만으로는 부족합니다. 기능적 가능, 유효 자격, 일정 여유, 사용 승인을 구분해 명시해야 개발자와 LLM이 모두 ‘대체 가능’으로 뭉뚱그리지 않습니다.

{{story:evidence}}

- 자격 범위: `Q03R`이 어떤 제품(`P-A` / `P-B`)·역량(`CAP-CUT`)·유효기간에 적용되는지 구분
- 상태 의미: 설비의 `available`이 생산 일정상 여유까지 뜻하는지 별도 정의

<!-- notes -->
온톨로지의 역할은 관계를 많이 만드는 것이 아니라 업무상 구분을 명시하는 데 있다. 기능적으로 작업할 수 있는 설비, 해당 제품의 유효한 자격을 가진 설비, 실제 일정에 배정할 수 있는 설비, 사용 승인을 받은 설비를 나눠야 한다. 이 구분이 없으면 개발자나 LLM이 모두 대체 가능이라는 말로 뭉뚱그리기 쉽다. 우리가 가상 공장 실험에서 실제로 부딪힌 문제와 가까운 가치다. 다만 RDF로 표현한다고 구분이 자동으로 생기는 것은 아니므로 모델링 단계에서 개념과 관계를 분명히 정의해야 한다.

## 04. 공통 규칙 공유와 공정한 비교 기준

> SHACL을 공통 규칙 산출물로 두면 여러 서비스가 어떤 버전의 조건으로 검사했는지 추적하기 쉬워집니다. 공정한 비교 대상은 공유 스키마·규칙·버전 관리를 갖춘 Python 시스템입니다.

{{story:change}}

- 챗봇·검색 API·품질 점검·데이터 적재가 각각 조건을 구현하면 한쪽만 수정될 위험
- 차이는 규칙이 특정 애플리케이션 코드에 묶이는 정도와 다른 도구에서 재사용할 수 있는 정도

<!-- notes -->
같은 자격 조건을 챗봇, 검색 API, 품질 점검, 데이터 적재에서 각각 구현하면 어느 한쪽만 수정될 수 있다. SHACL을 공통 규칙 산출물로 두면 이 서비스가 어떤 버전의 조건으로 검사했는지를 추적하기 쉬운 구조를 만들 수 있다. 물론 Python도 공통 라이브러리나 선언형 설정으로 충분히 할 수 있다. 비교 대상은 잘 정리되지 않은 Python 코드가 아니라 공유 스키마, 규칙, 버전 관리를 갖춘 Python 시스템이어야 공정하다.

## 05. 파이프라인 전반의 품질 관리 지점
<!-- fit:compact diagram-small -->

{{story:shared}}

| 지점 | 확인할 수 있는 내용 |
| --- | --- |
| 새 데이터 적재 | 필수 식별자·타입·참조가 갖춰졌는가 |
| 데이터 통합 | 두 출처가 같은 관계를 서로 다른 의미로 쓰고 있지는 않은가 |
| 자격·정책 변경 | 새 규칙에서 어떤 기존 기록이 조건을 만족하지 못하는가 |
| 질의 결과 전달 | 이번 판단에 필요한 필드와 연결이 제공됐는가 |

> SHACL은 최종 답변 직전뿐 아니라 데이터 적재·통합·정책 변경·질의 전달 단계에서도 유용합니다. 다만 검사 통과가 사실의 진위를 보증하지는 않습니다.

<!-- notes -->
SHACL은 최종 답변 직전뿐 아니라 데이터 적재와 변경 단계의 품질 관리에도 쓸 만하다. 특히 검색 결과 일부를 검사할 때는 원본 데이터의 결함인지, 조회 과정에서 빠진 것인지 구분해야 한다. 검사 통과는 선언한 조건의 충족일 뿐 사실의 진위를 보증하지 않는다. 원천 부재와 조회 누락, 그리고 외부 사실 여부를 가르는 경계는 우리 연구에서 계속 유지할 가치가 있다.

## 06. 추론·검증·사실 확인의 구분

<!-- chapter:제조 부품으로 이해하는 의미·추론 -->
{{story:threequestions}}

| 작업 | 묻는 질문 | 필요한 근거 |
| --- | --- | --- |
| 추론 | 정의와 기록에서 어떤 결론이 따라오는가 | 입력 사실 + 공리·규칙 |
| 데이터 검증 | 제출한 데이터가 조건을 만족하는가 | 검사할 그래프 + Shape |
| 현실의 사실 확인 | 기록과 결론이 실제 업무에서 맞는가 | 독립 자료·현장 확인·전문가 판단 |

> 입력이 틀리면 논리적으로 일관된 결론도 현실에서는 틀릴 수 있습니다.

<!-- notes -->
이 발표의 핵심 구분이다. 추론은 주어진 전제에 대한 작업이고 검증은 지정한 데이터 범위와 조건에 대한 작업이다. 둘 다 외부 사실을 자동으로 확인하지 않는다. 예를 들어 제조사가 다른 회사로 잘못 기록되어도 IRI 형식과 개수 조건은 만족할 수 있다. 사실 확인에는 별도 근거가 필요하며 전문가 판단도 그 출처와 절차를 기록해야 한다.

## 07. RDF·RDFS·OWL·SHACL의 역할

| 구성 | 역할 | 제조·설비 예 |
| --- | --- | --- |
| RDF | 개체·관계를 트리플로 표현 | P1은 조립품 A1에 장착된다 |
| RDFS | 클래스 포함 관계, domain/range 등 정의 | 볼트는 체결 부품, 체결 부품은 구성 부품 |
| OWL | 더 풍부한 논리적 공리 표현 | 역관계, 클래스 조합·배타성, 동일성 |
| 추론기 | 지원하는 공리·규칙의 결론 계산 | P1도 구성 부품이라는 타입 도출 |
| SHACL | 주어진 RDF의 조건 충족 검사 | 필수 제조사·자격 범위가 기록됐는가 |

> 온톨로지는 무엇을 어떤 관계로 해석할지 정하고 SHACL은 특정 용도의 조건 충족을 검사합니다. 둘 중 하나만 쓰는 설계도 가능합니다.

출처: [RDF](https://www.w3.org/TR/rdf11-primer/) · [RDFS](https://www.w3.org/TR/rdf-schema/) · [OWL](https://www.w3.org/TR/owl2-primer/) · [SHACL](https://www.w3.org/TR/shacl/)

<!-- notes -->
온톨로지와 SHACL을 구분한다. 클래스와 속성의 의미를 정한 정의를 바탕으로 구체적 개체의 기록을 연결한다. RDFS와 OWL의 정의도 RDF로 표현할 수 있다. 추론기는 이런 언어의 일부 또는 프로파일을 지원하는 소프트웨어다. pySHACL은 Python에서 SHACL을 실행하는 도구이며 추론 옵션도 제공하지만 추론과 검증은 서로 다른 단계다.

## 08. RDF 트리플과 제조 부품

> RDF는 개체와 관계를 식별자로 연결합니다. Turtle은 그 그래프를 텍스트로 적는 형식입니다.

{{story:sensortriple}}

```turtle
@prefix ex: <https://example.org/manufacturing/> .
ex:P1 a ex:Bolt ;                # P1은 볼트 개체
    ex:installedIn ex:A1 .       # P1은 조립품 A1에 장착
```

- 입력은 설명용 합성 부품 기록이며 실제 설치 사실 확인과는 별개

<!-- notes -->
P1과 A1는 교육용 합성 식별자다. ex: 접두사는 긴 IRI를 줄여 적은 것이며 a는 rdf:type의 축약이다. 주어와 술어와 목적어는 각각 누가, 어떤 관계로, 무엇과 연결되는지를 표현한다. 목적어는 이 예제처럼 다른 개체일 수도 있고 숫자나 문자열 리터럴일 수도 있다. 부품 예제 원본은 자료 창의 manufacturing-data.ttl이다.

## 09. 개체·클래스·포함 관계

> P1은 하나의 부품이고 Bolt는 그 부품이 속한 클래스입니다. 클래스 간 포함 관계와 개체의 소속을 구분합니다.

{{story:instance}}

```turtle
ex:P1 a ex:Bolt .                         # 개체 → 클래스
ex:Bolt rdfs:subClassOf ex:Fastener .      # 클래스 → 상위 클래스
```

출처: [RDFS 클래스와 인스턴스](https://www.w3.org/TR/rdf-schema/)

<!-- notes -->
개체와 클래스의 구분은 데이터 모델링의 출발점이다. 이 발표에서 P1은 개별 부품이고 Bolt와 Fastener는 클래스다. rdf:type은 개별 개체가 어떤 범주에 속하는지 나타내고 rdfs:subClassOf는 한 범주가 더 넓은 범주에 포함됨을 뜻한다.

## 10. RDFS 클래스 계층과 타입 추론
<!-- fit:compact -->

> 하위 클래스의 개체는 상위 클래스에도 속합니다. 점선은 정의를 적용해 얻는 추가 결론입니다.

{{story:sensorclasses}}

- 입력: `P1 a Bolt` + `Bolt ⊆ Fastener ⊆ Component`
- 출력: `P1 a Fastener`, `P1 a Component`
- 실제 부품의 정체가 맞는지는 원천 자료로 별도 확인

출처: [RDFS](https://www.w3.org/TR/rdf-schema/)

<!-- notes -->
하위 클래스의 모든 인스턴스가 상위 클래스에도 속한다는 정의를 사용한다. P1을 Component로 직접 입력하지 않아도 추론 결과에서 조회할 수 있다. 실제 실행 예제에서는 원본 조회, RDFS 규칙 적용, OWL-RL 규칙 적용의 결과를 별도로 저장했다. 이 예시로 전체 RDFS 또는 OWL 기능의 정확성을 평가하지 않는다.

## 11. domain·range의 타입 해석

> domain과 range는 관계의 주어·목적어를 어떤 타입으로 해석할지 정합니다. 입력을 거부하는 검증 규칙과는 다릅니다.

{{story:domainrange}}

```turtle
ex:installedIn rdfs:domain ex:Component ; # 주어는 구성 부품
               rdfs:range ex:Assembly . # 목적어는 조립품
```

출처: [RDFS domain/range](https://www.w3.org/TR/rdf-schema/)

<!-- notes -->
예를 들어 장비와 사람이 뒤바뀐 관계를 넣어도 domain과 range만으로 잘못된 입력이라고 차단하지 않는다. 관계에 따라 타입이 추론되어 붙는다. 별도로 배타적인 클래스 공리를 선언했고 같은 개체가 양쪽에 속하게 되면 논리 충돌이 생길 수 있다. 입력 단계에서 기대 타입을 확인하려면 SHACL이나 코드 기반의 명시적인 검증 정책이 필요하다.

## 12. OWL 공리와 역관계
<!-- fit:compact -->

> OWL의 공리는 관계와 클래스의 논리적 의미를 명시합니다. 실제 계산 범위는 선택한 추론기의 지원 기능에 달려 있습니다.

{{story:inverse}}

- `inverseOf`: P1이 A1에 장착되면 A1은 P1을 포함
- `equivalentClass`: “인증 부품이면서 체결 부품” 같은 분류 정의
- `disjointWith` / `sameAs`: 배타 분류 / 동일 개체 선언

출처: [OWL 2 Primer](https://www.w3.org/TR/owl2-primer/)

<!-- notes -->
역관계는 실제 작은 제조 예제에서 실행했다. 동치 클래스·배타 클래스·동일성은 기능 설명이다. 이 예제에서 모든 OWL 기능을 실행하거나 검증하지 않았다. 논리적 동치는 업무 의미 검토를 요구하며 같은 이름이라는 이유로 sameAs를 선언해서는 안 된다.

## 13. 열린 세계와 기록 부재

> 기록이 없다는 사실만으로 현실에서 거짓이라고 결론 내릴 수 없습니다. 제출 자료의 필수 항목 검사는 별도로 선언합니다.

{{story:openworld}}

- OWL: 추가 근거가 없으면 제조사나 갱신 자격의 실제 존재 판단을 유보
- SHACL: 제출된 기록에 필수 식별자가 없으면 `minCount` 위반

출처: [OWL 열린 세계 가정](https://www.w3.org/TR/owl2-primer/)

<!-- notes -->
긍정 사실을 도출하지 못했다는 것과 부정 사실을 도출했다는 것은 다르다. 가상 공장 실험에서도 조회되지 않은 자격이나 일정 정보를 원본에 없는 것으로 단정하지 않도록 구분했다. SHACL로 제출 자료의 필수 값 누락을 검사하면서 업무 판정을 unknown으로 정하는 방식도 가능하다. 이는 애플리케이션 정책이다.

## 14. 전체 조건·존재 조건·동일성
<!-- fit:compact -->

> “모두 인증 부품”이라는 조건은 연결 대상의 존재를 보장하지 않습니다. 식별자 두 개도 서로 다른 실체 둘을 자동으로 뜻하지 않습니다.

{{story:quantifiers}}

- `allValuesFrom`: 연결된 대상이 있다면 지정 클래스에 속함
- `someValuesFrom`: 지정 클래스에 속한 대상의 존재를 요구
- 다른 개체임을 명시하려면 별도 동일성·차이 선언과 근거 검토

출처: [OWL 제약과 동일성](https://www.w3.org/TR/owl2-primer/)

<!-- notes -->
모든 값 제한은 존재를 보장하지 않는다. 반면 존재 제한은 모델에서 어떤 대상이 존재해야 함을 뜻하지만 원본 파일에 이름 붙은 값을 채워 주는 입력 폼 검사가 아니다. 두 이름을 쓴 사실만으로 서로 다른 회사라고 확정하지 않으며 differentFrom 등 추가 선언이 필요할 수 있다.

## 17. 다단계 관계와 SKOS·OWL 구분
<!-- fit:compact -->

> 다단계 연결 계산은 도달 가능한 대상 쌍을 구하며 용어 분류(`skos:broader`)와 클래스 포함(`rdfs:subClassOf`)은 서로 다른 관계입니다.

{{story:skos_owl}}

- 다단계 도달: `(P1, A1), (A1, PRODUCT_X)`에서 `(P1, PRODUCT_X)` 도출
- 모델링 역할 구분: SKOS는 용어·분류 체계 연결, OWL/RDFS는 개체 타입과 논리 관계 정의

출처: [SKOS Primer](https://www.w3.org/TR/skos-primer/) · [OWL 2 Primer](https://www.w3.org/TR/owl2-primer/)

<!-- notes -->
여러 관계를 합쳐 도달 가능한 대상 쌍을 계산하는 작업과 용어·클래스 계층을 정의하는 작업은 구분해야 한다. skos:broader는 rdfs:subClassOf와 같지 않고 그 자체로 전이 속성도 아니다. SKOS 개념을 특정 OWL 클래스에 대응시키려면 별도 매핑을 정의해야 한다.

## 18. SHACL의 입력과 검사 결과

<!-- chapter:SHACL 검증과 도구·검토 기록 -->
{{story:shaclconcept}}

**SHACL**: Shapes Constraint Language. **Shape**: 검사 대상과 조건을 묶은 구조.

- Data Graph: 검사할 부품·설비 기록
- Shapes Graph: “필수 식별자와 적용 범위 조건이 기록돼야 한다”
- Validation Report: 어떤 개체·속성이 어떤 조건을 어겼는지 구조화해 기록

> SHACL 통과는 선언한 조건의 충족입니다. 기록된 정보가 현실에서 참이라는 인증은 아닙니다.

출처: [SHACL](https://www.w3.org/TR/shacl/)

<!-- notes -->
SHACL Shape 역시 RDF로 표현한다. 그림은 사람의 규정 문장을 조건으로 명시하고 데이터에 적용하는 흐름이다. 전체 세계가 닫혀 있다고 선언하는 것보다는 주어진 그래프를 정해진 검사 대상으로 삼는다고 설명하는 편이 정확하다. 필수 값이 없는 것은 minCount 위반이며 이 결과를 거부나 보류로 해석하는 것은 애플리케이션 정책이다.

## 19. 업무 문장의 Shape 변환

> Shape 작성은 요구 문장을 검사 대상·속성·개수·값 종류로 나누는 과정입니다. 뜻이 맞는지는 정상·위반·결측 반례로 확인합니다.

{{story:shapebuild}}

- `targetNode`는 특정 개체, `targetClass`는 클래스의 대상 개체를 선택
- 문법이 맞는 Shape도 잘못된 업무 조건을 검사할 수 있으므로 반례 점검이 필수

<!-- notes -->
Shape를 작성할 때는 도구 선택에 앞서 요구사항을 명확히 한다. 검사 대상, 속성, 자료형·개수·범위, 결측 처리와 적용 버전을 먼저 정한다. 자동 생성된 Shape가 문법 검사를 통과해도 순금액 대신 총금액을 검사하거나 불필요한 조건을 넣을 수 있으므로 정상·위반·결측·무관 변형 사례를 함께 확인한다.

## 22. LLM 도구 설계의 명시적 계약
<!-- fit:compact -->

> 미리 만든 쿼리를 LLM이 선택하는 구조에서는 도구마다 반환 범위와 후속 확인 조건을 계약으로 선언해 프롬프트 속 숨은 가정을 시스템 구성요소로 옮길 수 있습니다.

{{view:tool_contract}}

- 온톨로지는 개념을 정렬하고 SHACL은 입력 조건 충족을 검사하되 도구 오선택·질문 오해석까지 해결하지는 못함

<!-- notes -->
미리 작성한 쿼리 템플릿을 LLM이 선택하는 구조에서는 도구마다 무엇을 반환하고 무엇을 확인하지 않는지 선언해 둘 수 있다. 예를 들어 replacement_candidates는 기능적 후보만 반환하며 자격이나 일정까지 확인하지 않으므로 별도 자격 조회가 필요하다. 온톨로지는 도구들이 사용하는 개념을 맞추고 SHACL은 반환된 근거가 정해진 입력 조건을 갖췄는지 검사한다. 다만 LLM이 도구를 잘못 골랐거나 질문을 잘못 해석한 문제까지 검사기가 해결하지는 못한다.

## 24. 저장소 변경 시 의미를 유지하는 기준
<!-- fit:compact -->

> Neo4j와 RDF 저장소는 표현과 쿼리가 달라도 “같은 후보·같은 근거·같은 조건”을 반환해야 비교가 가능합니다. 공통 의미 모델은 이때 기준점이 됩니다.

{{view:backend_parity}}

- 가상 공장 **48쌍** 조회 일치 및 백엔드 변경 실험 검토 범위 축소(`32 → 20 → 10`) 확인 ([백엔드 검토 일지](../../journal/2026-11-06-backend-inference-review.md) · [가상 공장 대조 기록](../records/2026-11-10-factory-rdf-parity.json))

<!-- notes -->
Neo4j와 RDF 저장소는 표현과 쿼리가 달라도 같은 후보, 같은 근거, 같은 조건을 반환해야 비교가 가능하다. 공통 의미 모델은 이때 기준점이 된다. 가상 공장 로컬 비교에서는 정해진 48쌍의 조회 결과가 일치했고 Python과 SHACL 검토기도 6개 근거 묶음 모두에서 같은 플래그를 냈다. 별도 백엔드 실험에서는 Neo4j+n10s와 Neptune+외부 RDFS의 계층 추론 및 삭제·복원 후 재검토 범위를 확인했다. 이는 기준을 구현하고 확인할 수 있다는 작은 증거일 뿐 가상 공장 48쌍의 Neptune 실증이나 유지보수 비용 절감을 입증한 것은 아니다.

## 25. 도입 판단 기준과 연구의 의의
<!-- fit:compact -->

> 지금 연구의 방향은 “온톨로지를 쓰면 LLM이 더 똑똑해진다”보다 “LLM이 사용하는 근거와 판단 조건을 명시하고 공유하며 변경과 오류를 추적할 수 있게 한다”입니다.

{{view:adoption_guide}}

- 답변 개선은 특정 상황에서 가져올 수 있는 효과로 검증하고 구조 자체의 장점은 **재사용·변경 절차·추적 가능성**으로 따로 평가

<!-- notes -->
서비스 하나, 데이터 출처 하나, 규칙 몇 개가 안정적으로 유지되는 상황이라면 Python과 타입 스키마로 끝내는 편이 더 단순할 수 있다. RDF·OWL·SHACL을 도입하면 모델링, 매핑, 버전 관리라는 새로운 부담도 생긴다. 도입 시점은 데이터 건수보다 같은 의미를 여러 팀·서비스가 반복 정의하는지, 규칙 변경 때 수정 위치를 찾기 어려운지, 판단 근거와 규칙 버전을 나중에 설명해야 하는지, 출처나 저장소가 달라도 같은 해석을 유지해야 하는지로 판단하는 것이 좋다.
