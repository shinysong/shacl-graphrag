## 01. 소속 변경과 발주 승인

<!-- chapter:업무 질문과 데이터 -->
**“검토자의 소속 본부가 바뀌었습니다. 이 발주를 그대로 승인해도 되나요?”**

{{story:question}}

> 업무 설명용 합성 시나리오입니다. 판정과 함께 적용한 규칙, 사용한 근거, 재검토 대상을 제시하는 것이 목표입니다.

<!-- notes -->
구매 담당자의 실제 업무에서 나올 법한 질문으로 시작한다. 실기업에서 수집한 질문이나 운영 효과를 측정한 사례는 아니며 기존 발주·조직·검토자 합성 스키마를 설명하기 위해 만든 시나리오다. 소속 변경 전후를 추적하는 운영 시스템이 완성됐다는 뜻도 아니다. 뒤의 예제는 본부 충돌 입력으로 실행한다. 변경 후 상태에 해당하는 한 시점의 입력이다. 구매 담당자는 진행 가능 여부를, 승인 담당자는 규정 적용을, 감사 담당자는 판단 근거와 버전을 확인하려 한다. 이 요구에서 출발해 데이터의 의미와 규칙을 시스템 사이에서 공유하는 방식을 살펴본다.

## 02. 발표 구성

{{story:learning}}

- **업무 질문:** 판단에 필요한 데이터와 의미
- **제조 부품 예제:** 표현·추론·검증의 차이
- **연구 결과:** 검사한 입력·조건·출력
- **후속 설계:** 실제 자료의 한계와 데모 화면

<!-- notes -->
첨부 발표자료의 짧은 설명과 도식 중심 구성을 참고했다. 기술의 전체 목록을 소개하기보다 부품 하나를 끝까지 따라가며 입력, 정의, 추론, 검사, 사실 확인의 차이를 익힌다. 이후 발주 예제와 부품 인증 질문으로 돌아온다. 사용자가 제공한 영상 요약의 개념은 공식 표준과 대조했지만 원영상이나 자막 시각은 확인하지 않았으므로 영상 인용으로 제시하지 않는다. HTML은 외부 네트워크 없이 재생되며 자료 창에 코드와 실제 출력이 들어 있다.

## 03. 데이터의 의미·연결·시점

> **근거**는 판단에 사용한 기록이고 **시맨틱**은 그 기록의 뜻과 관계입니다. 같은 status라도 계약·승인·자격에서 의미가 다릅니다.

{{story:evidence}}

- 키로 연결: 부품 P1 → 계약 C7 → 검토자 R2 → 소속 이력
- 시점 확인: 승인 당시 소속과 현재 소속이 다르면 어느 규칙을 적용할지 결정

설명용 합성 레코드 · 이력은 개념 예시이며 실제 실행 입력은 한 시점의 스냅샷

<!-- notes -->
세 시스템에서 승인·조직·정책 정보를 가져와도 바로 결론을 내릴 수는 없다. 같은 status라는 이름도 계약 유효 상태, 검토 결정, 사람의 자격 상태를 가리킬 수 있다. 값의 단위, 식별자 대응, 관계의 방향, 유효 시점을 계약으로 정해야 한다. 근거에는 출처와 시점도 필요하지만 이번 작은 실행 예제가 시간에 따른 변경 이력이나 근거 최신성까지 검증한 것은 아니다. semantic을 어려운 추상 개념 대신 데이터 항목의 뜻과 연결 규칙으로 소개한다. RDF로 변환하는 것만으로 이 의미가 자동 결정되지는 않는다.

## 04. 규칙 변경의 담당자와 요구사항

> 기존 Python·SQL·룰 엔진·DAG로도 구현할 수 있습니다. 연구의 관심은 변경된 의미와 규칙을 여러 소비처에 일관되게 전달하는 방법입니다.

{{story:change}}

- 공유 JSON·스키마 레지스트리·공통 라이브러리도 비교 대상
- 표준 형식 도입만으로 변경 비용과 배포 문제가 사라지지는 않음

<!-- notes -->
기존 시스템이 이 일을 할 수 없어서 연구를 시작한 것은 아니다. SQL 조인이나 Python 함수, 룰 엔진, DAG 기반 파이프라인으로 같은 결정을 구현할 수 있다. 규칙이 바뀔 때 그 의미를 어디에서 관리하고 어떤 시스템에 변경을 반영해야 하는지 추적하는 문제에 관심을 둔다. DAG는 실행 순서와 의존성을 표현하는 데 쓸 수 있고 노드에 공유 규칙을 연결할 수도 있다. 따라서 DAG와 의미 계층은 배타적인 대안이 아니다. 시스템별 복제만을 기존 방식의 필연적 한계로 설정하지 않는다. 사람의 변경 작업 시간, 자연 발생 배포 오류율, 표준 도입의 장기 비용 절감은 이번 자료에서 측정하지 않았다.

## 05. 공유 의미와 검사 계약
<!-- fit:compact diagram-small -->

{{story:shared}}

| 구성 | 공유하려는 내용 |
| --- | --- |
| RDF | 개체의 식별자와 관계 표현 |
| OWL | 클래스·관계의 공리와 함의의 기준 |
| SHACL / Shape | 검사 대상과 조건을 담은 규칙 구조 |
| pySHACL | Shape를 실행해 표준 검증 보고서 생성 |

> 연구 의도는 의미와 검사 조건을 공통 자산으로 관리하는 것입니다. 매핑, 버전 배포, 접근 제어와 회귀 테스트는 별도로 구현해야 합니다.

출처: [RDF](https://www.w3.org/TR/rdf11-primer/) · [OWL](https://www.w3.org/TR/owl2-primer/) · [SHACL](https://www.w3.org/TR/shacl/) · [pySHACL](https://github.com/RDFLib/pySHACL)

<!-- notes -->
그림은 지향하는 공유 구조이며 실제 세 시스템을 배포해 유지보수 개선을 측정한 결과가 아니다. 데이터 원본을 모두 RDF 저장소로 옮길 필요 없이 필요한 부분만 공통 식별자와 관계로 투영할 수 있다. OWL로 클래스와 관계의 논리 의미를 선언하고 SHACL Shape로 업무 검사 조건을 표현한다. 특정 애플리케이션 안에만 숨기지 않고 검토·교환 가능한 형태로 두려 한다. 이식성은 사용하는 언어 기능, 추론 프로파일, 엔진 지원을 확인해야 한다. 공통 JSON이나 라이브러리도 공유할 수 있으므로 표준 형식이라는 이유만으로 더 우수하다고 결론 내리지 않는다. RDF는 데이터 모델이고 Turtle은 표기 형식이다. OWL 추론과 SHACL 검증은 별개이며 통합 진단은 OWL-RL을 실행하지 않는다.

## 06. 추론·검증·사실 확인의 구분

<!-- chapter:제조 부품으로 이해하는 의미·추론 -->
{{story:threequestions}}

| 작업 | 묻는 질문 | 필요한 근거 |
| --- | --- | --- |
| 추론 | 정의와 기록에서 어떤 결론이 따라오는가 | 입력 사실 + 공리·규칙 |
| 데이터 검증 | 제출한 데이터가 조건을 만족하는가 | 검사할 그래프 + Shape |
| 현실의 사실 확인 | 기록과 결론이 실제 업무에서 맞는가 | 독립 자료·현장 확인·전문가 판단 |

> 입력이 틀리면 논리적으로 일관된 결론도 현실에서는 틀릴 수 있습니다.

<!-- notes -->
이 발표의 핵심 구분이다. 추론은 주어진 전제에 대한 작업이고 검증은 지정한 데이터 범위와 조건에 대한 작업이다. 둘 다 외부 사실을 자동으로 확인하지 않는다. 예를 들어 제조사가 다른 회사로 잘못 기록되어도 IRI 형식과 개수 조건은 만족할 수 있다. 사실 확인에는 별도 근거가 필요하며 전문가 판단도 그 출처와 절차를 기록해야 한다.

## 07. RDF·RDFS·OWL·SHACL의 역할

| 구성 | 역할 | 부품 P1 예 |
| --- | --- | --- |
| RDF | 개체·관계를 트리플로 표현 | P1은 조립품 A1에 장착된다 |
| RDFS | 클래스 포함 관계, domain/range 등 정의 | 볼트는 부품, 부품은 구성 부품 |
| OWL | 더 풍부한 논리적 공리 표현 | 역관계, 클래스 조합·배타성, 동일성 |
| 추론기 | 지원하는 공리·규칙의 결론 계산 | P1도 구성 부품이라는 타입 도출 |
| SHACL | 주어진 RDF의 조건 충족 검사 | 제조사 식별자가 기록됐는가 |

> 언어·정의와 실행 도구를 구분합니다. 파일을 읽는 것만으로 추론이 켜지지는 않습니다.

출처: [RDF](https://www.w3.org/TR/rdf11-primer/) · [RDFS](https://www.w3.org/TR/rdf-schema/) · [OWL](https://www.w3.org/TR/owl2-primer/) · [SHACL](https://www.w3.org/TR/shacl/)

<!-- notes -->
온톨로지와 지식 그래프를 구분한다. 클래스와 속성의 의미를 정한 정의를 바탕으로 구체적 개체의 기록을 연결한다. RDFS와 OWL의 정의도 RDF로 표현할 수 있다. 추론기는 이런 언어의 일부 또는 프로파일을 지원하는 소프트웨어다. pySHACL은 Python에서 SHACL을 실행하는 도구이며 추론 옵션도 제공하지만 추론과 검증은 서로 다른 단계다.

## 08. RDF 트리플과 제조 부품

> RDF는 개체와 관계를 식별자로 연결합니다. Turtle은 그 그래프를 텍스트로 적는 형식입니다.

{{story:sensortriple}}

```turtle
@prefix ex: <https://example.org/manufacturing/> .
ex:P1 a ex:Bolt ;                # P1은 볼트 개체
    ex:installedIn ex:A1 .       # P1은 조립품 A1에 장착
```

- 입력은 설명용 합성 부품 기록이며 실제 설치 사실 확인과는 별개

<!-- notes -->
P1과 A1는 교육용 합성 식별자다. ex: 접두사는 긴 IRI를 줄여 적은 것이며 a는 rdf:type의 축약이다. 주어와 술어와 목적어는 각각 누가, 어떤 관계로, 무엇과 연결되는지를 표현한다. 목적어는 이 예제처럼 다른 개체일 수도 있고 숫자나 문자열 리터럴일 수도 있다. 부품 예제 원본은 자료 창의 manufacturing-data.ttl이다.

## 09. 개체·클래스·포함 관계

> P1은 하나의 부품이고 Bolt는 그 부품이 속한 클래스입니다. 클래스 간 포함 관계와 개체의 소속을 구분합니다.

{{story:instance}}

```turtle
ex:P1 a ex:Bolt .                         # 개체 → 클래스
ex:Bolt rdfs:subClassOf ex:Fastener .      # 클래스 → 상위 클래스
```

출처: [RDFS 클래스와 인스턴스](https://www.w3.org/TR/rdf-schema/)

<!-- notes -->
사용자가 제공한 자막 요약에서 지적한 개체·클래스 혼동을 개념 수준에서 바로잡았다. 원영상의 특정 시점이 실제로 어떤 표현을 썼는지는 확인하지 않았다. 이 발표에서 P1은 개별 부품이고 Bolt와 Fastener는 클래스다. 고급 OWL 모델링에서 한 IRI를 여러 역할로 쓰는 기능은 이 입문 예제의 범위 밖이다.

## 10. RDFS 클래스 계층과 타입 추론
<!-- fit:compact -->

> 하위 클래스의 개체는 상위 클래스에도 속합니다. 점선은 정의를 적용해 얻는 추가 결론입니다.

{{story:sensorclasses}}

- 입력: `P1 a Bolt` + `Bolt ⊆ Fastener ⊆ Component`
- 출력: `P1 a Fastener`, `P1 a Component`
- 실제 부품의 정체가 맞는지는 원천 자료로 별도 확인

출처: [RDFS](https://www.w3.org/TR/rdf-schema/)

<!-- notes -->
하위 클래스의 모든 인스턴스가 상위 클래스에도 속한다는 정의를 사용한다. P1을 Component로 직접 입력하지 않아도 추론 결과에서 조회할 수 있다. 실제 실행 예제에서는 원본 조회, RDFS 규칙 적용, OWL-RL 규칙 적용의 결과를 별도로 저장했다. 이 예시로 전체 RDFS 또는 OWL 기능의 정확성을 평가하지 않는다.

## 11. domain·range의 타입 해석

> domain과 range는 관계의 주어·목적어를 어떤 타입으로 해석할지 정합니다. 입력을 거부하는 검증 규칙과는 다릅니다.

{{story:domainrange}}

```turtle
ex:installedIn rdfs:domain ex:Component ; # 주어는 구성 부품
               rdfs:range ex:Assembly . # 목적어는 조립품
```

출처: [RDFS domain/range](https://www.w3.org/TR/rdf-schema/)

<!-- notes -->
예를 들어 장비와 사람이 뒤바뀐 관계를 넣어도 domain과 range만으로 잘못된 입력이라고 차단하지 않는다. 관계에 따라 타입이 붙는다. 별도로 배타적인 클래스 공리를 선언했고 같은 개체가 양쪽에 속하게 되면 논리 충돌이 생길 수 있다. RDFS 자체에는 OWL의 배타 클래스 공리가 없다는 점도 구분한다. 입력 단계에서 기대 타입을 확인하려면 명시적인 검증 정책이 필요하다.

## 12. OWL 공리와 역관계
<!-- fit:compact -->

> OWL의 공리는 관계와 클래스의 논리적 의미를 명시합니다. 실제 계산 범위는 선택한 추론기의 지원 기능에 달려 있습니다.

{{story:inverse}}

- `inverseOf`: P1이 A1에 장착되면 A1은 P1을 포함
- `equivalentClass`: “인증 부품이면서 체결 부품” 같은 분류 정의
- `disjointWith` / `sameAs`: 배타 분류 / 동일 개체 선언

출처: [OWL 2 Primer](https://www.w3.org/TR/owl2-primer/)

<!-- notes -->
역관계는 실제 작은 제조 예제에서 실행했다. 동치 클래스·배타 클래스·동일성은 기능 설명이다. 이 예제에서 모든 OWL 기능을 실행하거나 검증하지 않았다. 논리적 동치는 업무 의미 검토를 요구하며 같은 이름이라는 이유로 sameAs를 선언해서는 안 된다.

## 13. 열린 세계와 기록 부재

> 제조사 기록이 없다는 사실만으로 제조사가 존재하지 않는다고 결론 내릴 수 없습니다. 제출 자료의 필수 항목 검사는 별도로 선언합니다.

{{story:openworld}}

- OWL: 추가 근거가 없으면 제조사에 대한 판단을 유보
- SHACL: 제출된 P1 기록에 제조사 IRI가 없으면 `minCount` 위반

출처: [OWL 열린 세계 가정](https://www.w3.org/TR/owl2-primer/)

<!-- notes -->
긍정 사실을 도출하지 못했다는 것과 부정 사실을 도출했다는 것은 다르다. 별도 공리나 명시적 부정으로 결론을 낼 수 있는 경우는 이 설명에서 제외한다. 여기서는 그런 추가 정보가 없는 상황을 설명한다. SHACL로 제출 자료의 필수 값 누락을 검사하면서 업무 판정을 unknown으로 정하는 방식도 가능하다. 이는 애플리케이션 정책이다.

## 14. 전체 조건·존재 조건·동일성
<!-- fit:compact -->

> “모두 인증 부품”이라는 조건은 연결 대상의 존재를 보장하지 않습니다. 식별자 두 개도 서로 다른 실체 둘을 자동으로 뜻하지 않습니다.

{{story:quantifiers}}

- `allValuesFrom`: 연결된 대상이 있다면 지정 클래스에 속함
- `someValuesFrom`: 지정 클래스에 속한 대상의 존재를 요구
- 다른 회사임을 명시하려면 별도 동일성·차이 선언과 근거 검토

출처: [OWL 제약과 동일성](https://www.w3.org/TR/owl2-primer/)

<!-- notes -->
모든 값 제한은 존재를 보장하지 않는다. 반면 존재 제한은 모델에서 어떤 대상이 존재해야 함을 뜻하지만 원본 파일에 이름 붙은 값을 채워 주는 입력 폼 검사가 아니다. 두 이름을 쓴 사실만으로 서로 다른 회사라고 확정하지 않으며 differentFrom 등 추가 선언이 필요할 수 있다. SHACL은 선택한 그래프에서 속성 경로의 값 노드를 세므로 동일성 추론을 사전에 적용할지에 따라서도 정책을 정해야 한다.

## 17. 조회 실패와 현실의 거짓

> 단순 ASK의 false는 선택한 그래프에서 해당 패턴을 찾지 못했다는 뜻입니다. 현실에서 거짓이라는 판정과 구분합니다.

{{story:querymeaning}}

```sparql
ASK { ex:P1 a ex:Component }  # P1의 Component 타입이 조회되는가
```

- 원본 false → 확장본 true: 새 사실을 외부에서 확인한 것이 아니라 정의를 적용한 결과

<!-- notes -->
SPARQL ASK는 질의 패턴이 활성 그래프와 적용된 entailment regime에서 해를 갖는지 반환한다. 여기서는 직접 트리플 멤버십과 동등한 단일 패턴을 설명한다. 명시적 부정이나 추가 공리를 이용하는 다른 논리 판단까지 같은 설명으로 뭉뚱그리지 않는다. 원본 조회 결과와 추론 그래프의 조회 결과가 달라져도 원본 파일이 저절로 수정된 것은 아니다.

## 18. 다단계 관계의 고정점 계산

> 여러 관계를 합쳐 도달 가능한 대상 쌍을 계산합니다. 가능한 모든 경로를 나열하는 작업과는 다릅니다.

{{story:reachability}}

```text
edge(P1, A1), edge(A1, PRODUCT_X)
reach(X, Y) ← edge(X, Y)                  # 직접 연결도 도달
reach(X, Z) ← reach(X, Y), edge(Y, Z)     # 도달 관계를 연장
```

- 실제 Python 집합 계산의 추가 결과: `(P1, PRODUCT_X)`

<!-- notes -->
규칙은 설명용 Datalog식 표기다. 실제 제조 교육용 실행은 동일한 양의 관계를 Python 집합으로 고정점까지 계산했다. 별도 Datalog 엔진을 실행한 것은 아니다. 이 결과 자체로 재검토 의무나 제품 안전성을 결정하지 않는다. 원천 관계와 적용 정책은 별도로 검토한다.

## 20. SHACL의 입력과 검사 결과

<!-- chapter:지식 그래프 구축과 SHACL -->
{{story:shaclconcept}}

**SHACL**: Shapes Constraint Language. **Shape**: 검사 대상과 조건을 묶은 구조.

- Data Graph: 검사할 부품 기록
- Shapes Graph: “P1에 제조사 IRI가 하나 이상 있어야 한다”
- Validation Report: 어떤 개체·속성이 어떤 조건을 어겼는지 기록

> SHACL 통과는 선언한 조건의 충족입니다. 제조사 정보가 현실에서 참이라는 인증은 아닙니다.

출처: [SHACL](https://www.w3.org/TR/shacl/)

<!-- notes -->
SHACL Shape 역시 RDF로 표현한다. 그림은 사람의 규정 문장을 조건으로 명시하고 데이터에 적용하는 흐름이다. 전체 세계가 닫혀 있다고 선언하는 것보다는 주어진 그래프를 정해진 검사 대상으로 삼는다고 설명하는 편이 정확하다. 필수 값이 없는 것은 minCount 위반이며 이 결과를 거부나 보류로 해석하는 것은 애플리케이션 정책이다.

## 21. 업무 문장의 Shape 변환

> Shape 작성은 요구 문장을 검사 대상·속성·개수·값 종류로 나누는 과정입니다. 뜻이 맞는지는 정상·위반·결측 반례로 확인합니다.

{{story:shapebuild}}

- `targetNode`는 특정 개체, `targetClass`는 클래스의 대상 개체를 선택
- 문법이 맞는 Shape도 잘못된 업무 조건을 검사할 수 있음

<!-- notes -->
Shape를 작성할 때는 도구 선택에 앞서 요구사항을 명확히 한다. 검사 대상, 속성, 자료형·개수·범위, 결측 처리와 적용 버전을 먼저 정한다. targetClass로 클래스 전체를 대상으로 삼을 수도 있다. 자동 생성된 Shape가 문법 검사를 통과해도 순금액 대신 총금액을 검사하거나 불필요한 조건을 넣을 수 있으므로 정상·위반·결측·무관 변형 사례를 함께 확인한다. LLM이 만든 초안을 실행 전 정답으로 수리하는 실험을 뜻하지 않는다.

## 27. 검사 범위와 추론 설정

{{data:validation_scope}}

```turtle
# 두 번째 Shape: Component 타입 트리플이 실제로 있어야 함
sh:path rdf:type ; sh:hasValue ex:Component .
```

> 두 검사에서 제조사 기록 부재는 남습니다. 이 예제는 `sh:class` 대신 명시적 타입 값의 존재를 검사해 입력 범위 차이를 보여 줍니다.

<!-- notes -->
동일한 두 Shape를 원본, RDFS 확장본, OWL-RL 확장본에 적용했다. 제조사 minCount와 rdf:type 경로의 hasValue Component를 검사한다. 원본에서는 둘 다 위반하고 확장본에서는 제조사만 위반한다. SHACL의 class 검사는 데이터 그래프의 하위 클래스 관계도 반영할 수 있으므로 sh:class가 무조건 원본에서 실패한다고 설명하지 않는다. 또한 추론으로 검사 대상 클래스가 늘거나 값 개수가 달라질 수 있으므로 검사 범위를 실행 전에 정해야 한다.

## 38. 부품 인증 만료의 영향 범위
<!-- fit:compact -->

{{story:impact}}

“이 부품의 인증서가 만료됐습니다. **어떤 완제품을 재검토해야 하나요?**”

- 사용 관계: 인증서 → 부품 → 조립품 → 완제품
- 적용 조건: 부품 유형 → 상위 유형 → 적용 규정
- 판정: 해당 시점·규정에서 재검토 후보인지 확인

> 후속 설계안입니다. 재검토 후보 도출은 물리적 고장 예측이나 제품 안전성 판정이 아닙니다.

<!-- notes -->
기존 change-impact 연구와 관련된 질문이다. 이 도식의 새 결합 설계는 실행하지 않았다. 부품 인증, 구성 관계, 분류, 적용 규정, 시점과 버전이 함께 필요하다. 인증 만료라는 상태와 재검토 의무를 연결하는 규정은 제공된 계약으로 따로 명시해야 한다. 연결된 모든 제품이 곧바로 위험하다고 결론 내리지 않는다. 공개 ERP 스키마를 참고해 만든 거래·구성 사례는 여전히 합성 자료다.

## 40. 후속 가설과 평가 지표

| 제안 가설 | 통제할 것 | 관측할 것 |
| --- | --- | --- |
| 관계 계산이 LLM의 누락·오연결을 줄이는가 | 같은 질문·입력·정책 | 후보 재현율·정밀도, 잘못된 확답 |
| 공유 의미 정의가 질문 간 불일치를 줄이는가 | 동일 버전·정보 접근 | 질문 간 모순, 변경 후 회귀 오류 |
| 구현 차이가 변경·근거 추적 비용에 나타나는가 | 동등한 공리·규칙 | 실제 수정·테스트·추적 작업량 |
| 불완전한 근거에서 균형 있게 보류하는가 | 답변 가능 여부 | 잘못된 확답 + 불필요한 보류 |

> 모두 **제안 가설**입니다. 완료된 연구의 사전등록 가설이나 새 측정 결과로 제시하지 않습니다.

<!-- notes -->
공유 방식의 효과와 구현 언어의 효과를 섞지 않는다. 공유 코드·공유 JSON과 공유 OWL·SHACL을 대등하게 비교하고 동일한 버전 장애 조건을 적용해야 한다. 비용 지표는 사람의 실제 작업 시간을 측정할 계획이 있을 때만 유지보수 시간이라고 부른다. 단순 코드 줄 수나 반복 출력 수를 독립 관측값으로 취급하지 않는다. 가설과 분석 계획은 새 평가 자료를 보기 전에 고정해야 한다.

## 41. 동일 의미·정보를 받은 비교 조건
<!-- fit:compact -->

{{story:comparators}}

| 대조 | 분리하려는 차이 |
| --- | --- |
| 명시 조회 ↔ 같은 정책의 관계 계산 | 계산을 추가한 효과 |
| Python·재귀 SQL ↔ RDF·규칙/OWL | 같은 의미의 구현 방식 |
| 개별 설정 ↔ 공유 JSON/스키마 ↔ 공유 온톨로지 | 의미·버전 공유 방식 |
| 동일 보고서 유무를 바꾼 LLM | 계산된 근거를 제공한 효과 |

> 순서·도구 호출은 DAG로 구성할 수 있습니다. 모든 조합을 한꺼번에 돌리기보다 하나의 효과씩 분리합니다.

<!-- notes -->
추론 기능이 없는 대조군을 OWL보다 못한 구현이라고 평가해서는 안 된다. 명시 조회는 기능 제거 대조다. 구현 비교에서는 동일한 공리와 규칙, 입력, 결측 정책, 결과 범위와 근거 제공 수준을 맞춘다. 공유 기능이 있는 Python 대조군도 필요하다. SQL과 OWL의 표현력 전체가 동일하다는 주장이 아니라 선택한 유한 업무 규칙을 동등하게 구현하는 설계다. 새 유료 LLM 실험은 별도 범위와 예산 승인이 필요하다.

## 42. 여섯 가지 근거 상태

> 같은 질문에 서로 다른 근거 상태를 만들어 잘못된 확답과 불필요한 보류를 함께 확인합니다. 아래는 후속 데이터셋의 설명용 설계입니다.

{{view:state_matrix}}

- 원천·검색 반환·질문 시점·평가 기준을 별도로 저장
- 숨은 평가 기준으로 실행 답을 수정하지 않음

<!-- notes -->
여섯 상태는 새 데이터셋 설계 제안이다. 과거 연구에서는 일부 조건을 다뤘다. 모든 조건을 한 코호트에서 새로 실행한 것은 아니다. 원천 부재와 검색 누락은 원천 스냅샷과 실제 반환 자료를 따로 저장해야 구분할 수 있다. 충돌의 우선순위 정책은 평가 전에 정한다. 내부적으로 일관된 거짓 입력은 외부 평가 자료로만 드러날 수 있고 그 기준을 런타임 오라클로 전달해서는 안 된다.

## 43. 원천·합성·평가 자료의 구분

{{story:provenance}}

- 원천: 파일·해시·출처·사용 조건·시점·버전
- 작성 부분: 합성 관계와 가정한 규칙을 별도 표시
- 실행 근거: 실제 검색 반환과 추론·검증 설정 저장
- 평가 기준: 계약 일치와 외부 사실 판단을 별도 기록

> 실제 스키마를 참고해 만든 거래 데이터는 합성 데이터입니다. 사용한 코호트를 새 held-out 자료처럼 재사용하지 않습니다.

<!-- notes -->
다음 단계에서는 사례별로 어떤 추가 관계와 의미 정의가 답을 바꾸는지 표로 고정한다. 새 대규모 실행은 하지 않는다. 실제 공개 원천에서 확인한 관계와 연구자가 작성한 관계·규칙을 나눠야 한다. 기존 실제 자료의 출처와 라이선스를 유지하고 수집 실패도 남긴다. 평가 기준 답은 실행 경로에 전달하지 않는다. 계약 일치와 외부 사실 정확도를 같은 열에 합치지 않는다.

## 44. 관계 변경과 스키마 관리

> 관계는 바뀝니다. 안정된 식별자, 입력 매핑, 의미 변경, 시점·버전을 구분해 관리하는 범위를 작게 시작할 필요가 있습니다.

{{view:relation_change}}

- 운영 설계 제안: 영향받는 질의·Shape·소비처를 회귀 사례로 확인
- 실제 유지보수 시간과 장기 비용 절감은 아직 측정하지 않음

<!-- notes -->
제안하는 운영 절차에서 정책 담당자는 뜻과 적용 범위를 정한다. 개발 담당자가 매핑·규칙·테스트를 변경한 뒤 운영 담당자가 버전을 배포하고 영향받는 요청을 재검토한다. 표준 스키마를 만든 뒤에도 유지보수는 필요하다. 공유 JSON, 공통 라이브러리, 스키마 레지스트리도 같은 절차에 들어갈 수 있다. 연구에서는 같은 정책과 같은 정보를 제공하는 비교를 유지해야 한다. 형식에 맞는 거짓 사실, 숨은 원천 누락, 잘못 선택한 질문 계약은 검증 통과만으로 해결되지 않는다.

{{view:final_demo}}

<!-- notes -->
도입의 소속 변경 질문으로 돌아온다. 실제 코드는 변경 후 한 시점의 합성 입력으로 실행했다. 여기서 말하는 답은 그 실행을 설명하는 예시다. 정책 판정 blocked, 위반 division-separation, 요청 부서 DEPT_REQ, 검토자 USER_PRIMARY, 공통 본부 DIV_SALES는 저장된 입력과 보고서로 확인할 수 있다. 한국어 문장은 발표자가 작성한 요약이며 LLM의 실제 응답이 아니다. 변경 전후 비교·재검토 대상 자동 선정·실운영 승인 이력 관리는 목표 업무 흐름으로 설명했으며 이번 작은 예제에서 측정하지 않았다. 전체 예제와 프롬프트는 자료 버튼에서 확인하고 저장할 수 있다. 다음 검증에서는 같은 구조화 보고서를 제공하는 Python·SQL·SHACL 조건, 자연어 계약 선택 오류, 설명의 근거 일치, 실제 유지보수 작업을 분리해 측정해야 한다.
