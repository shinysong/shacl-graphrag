# 승인과 근거 버전의 일치 검사

## 실험 목적

기존 워크플로우에 붙일 작은 검사 기능을 검토한다. 검사 대상은 승인 당시의 대상·규칙·근거가 실행 직전에도 같은지다. 전체 데이터를 RDF로 옮기거나 오케스트레이션 엔진을 새로 만드는 작업은 포함하지 않는다.

예를 들어 제품 A의 부품 검토가 끝난 뒤 부품 사양이 바뀌었다면, 이전 승인을 그대로 사용할 수 있는지 확인한다. 관계없는 제품 B의 자료만 바뀌었다면 A의 승인을 다시 검사할 필요가 없을 수 있다. 이 구분에는 승인과 근거의 연결 기록이 필요하다.

```text
LLM 또는 애플리케이션의 실행 제안
                 ↓
호스트가 현재 대상·규칙·근거 버전을 수집
                 ↓
       같은 입력으로 두 구현 비교
       ├─ JSON + Python 규칙
       └─ RDF 변환 + 실제 SHACL 검사
                 ↓
   allow / deny / unknown + 사유
                 ↓
호스트가 실행 시점의 버전을 다시 확인하고 집행
```

LLM은 이 구조에서 행동을 제안할 수 있다. 이번 소프트웨어 점검에서는 사람이 작성한 입력을 사용하므로 LLM의 해석이나 도구 선택을 평가하지 않는다. 실행 제안과 최종 집행 사이의 버전 경쟁도 아직 구현하지 않았다.

## 기존 도구와의 중복

| 기존 작업 | 이미 다루는 기능 | 이번 작업의 경계 |
| --- | --- | --- |
| [OPA Agent Tool Calling](https://www.openpolicyagent.org/docs/agent-tool-calling) | LLM 도구 호출과 파라미터 검사, 거절 이유 전달, 정책 갱신과 결정 로그 | 도구 호출 검사 자체를 차별점으로 삼지 않는다. |
| [Cedar level validation](https://docs.cedarpolicy.com/policies/level-validation.html) | 정책의 참조 깊이를 제한하고 필요한 엔티티를 잘라 같은 결정을 유지 | 필요한 관계만 가져오는 기능만으로 새롭다고 주장하지 않는다. |
| [SHACL Validation under Graph Updates](https://arxiv.org/abs/2508.00137) | 갱신 연산 뒤에도 제약이 보존되는지를 정적으로 분석 | 이 논문은 이번 구현의 실행 중 부분 재검사 성능을 입증하는 자료가 아니다. |
| [PROV-O](https://www.w3.org/TR/prov-o/) | 엔티티·활동·파생 관계의 출처 표현 | 근거 의존성 표현 자체의 발명으로 설명하지 않는다. |

OPA와 Cedar는 문헌으로 비교했으며 이번에 실행하지 않았다. 차별점 후보는 여러 시스템의 승인과 근거를 적은 연결 코드로 검사하고 변경 이유를 추적하는 데 있다. 실제 연결 비용을 아직 측정하지 않았으므로 라이브러리의 필요성이 입증된 상태는 아니다.

## 검사 계약과 입력 책임

요청과 승인에 같은 대상 ID, 대상 버전, 규칙 버전이 있어야 한다. 승인이 유효하고 선언된 각 근거의 승인 당시 버전과 현재 버전이 같으면 `allow`다. 서로 다른 값이 확인되면 `deny`, 필드가 빠졌거나 입력이 불완전하면 `unknown`을 반환한다. `unknown`도 실행 허가는 아니다.

완전성은 호스트가 선언한다. 근거를 누락하고도 완전하다고 보내면 검사기가 알아낼 수 없다. 의존 근거가 없다는 명시적 선언은 허용하지만 실제 누락을 자동으로 찾아낸다는 뜻은 아니다. 버전 문자열의 일치는 원본 내용의 정확성이나 승인자의 권한을 증명하지 않는다.

두 구현은 입력 형식 검사와 불완전성 처리를 공유한다. 정상 입력의 판단은 Python 규칙과 SHACL 제약으로 각각 수행한다. RDF 구현은 `sh:equals`, `sh:hasValue`와 중복 근거 충돌을 찾는 SHACL-SPARQL을 사용하며 OWL 추론은 하지 않는다. 변경된 근거에서 영향받는 승인을 찾는 함수는 두 구현이 공유하는 직접 의존성 조회다. 이를 SHACL의 성과로 계산하지 않는다.

## 적용 판단 기준

단순한 버전 비교만 필요하다면 Python 규칙으로 충분할 수 있다. RDF를 이미 사용하는 시스템에서 제약 정의와 검사 보고서를 재사용할 수 있는지가 다음 검토 대상이다. 기존의 공유 의미 규칙 실험에서도 같은 정책의 JSON과 RDF 판단은 일치했다. 이번 점검은 그 결과를 새로운 정확도 향상으로 해석하지 않는다.

별도 라이브러리를 만들기 전에 서로 다른 두 워크플로우에 연결해 실제 필드 매핑, 규칙 변경, 테스트 수정, 오류 설명에 드는 작업을 기록한다. JSON이나 OPA 구현에도 같은 규칙과 근거를 주고 비교해야 한다. 연결 비용을 줄이지 못하면 사례·테스트·어댑터를 기존 도구에 기여하는 편이 낫다.

동적 온톨로지와 필요한 개념만 추출하는 연구는 후속 범위다. 자동으로 찾은 관계를 완전한 의존성으로 신뢰하려면 별도의 검증이 필요하다.

## 첫 실행 결과

2026-10-15에 직접 작성한 12개 사례를 두 구현으로 실행했다. 각 구현에서 허용 4건, 거절 7건, 정보 부족 1건이 나왔다. 12개 모두 상태와 사유 코드가 일치했다. 이는 예제 계약의 구현 일치이며 업무 정확도 100%를 뜻하지 않는다.

SHACL은 11건에서 실제로 실행됐다. 필드가 빠진 1건은 공통 입력 검사에서 `unknown`으로 끝났으므로 SHACL이 잡은 오류로 세지 않는다. 불완전한 입력과 확인된 위반이 동시에 있는 경우도 `unknown`을 우선하며 이 경계는 12개 사례와 별도의 단위 테스트에서 점검한다.

| 입력 상황 | Python | SHACL 경로 |
| --- | --- | --- |
| 대상·규칙·근거 버전 일치 | 허용 | 검사 후 허용 |
| 다른 대상에 대한 승인 | 거절 | 검사 후 거절 |
| 대상 버전 또는 규칙 버전 변경 | 거절 | 검사 후 거절 |
| 의존 근거 버전 변경 | 거절 | 검사 후 거절 |
| 관계없는 자료 변경 | 허용 | 검사 후 허용 |
| 승인 대상 버전 누락 | 정보 부족 | 실제 검사 전 종료 |
| 승인 철회 | 거절 | 검사 후 거절 |
| 같은 근거 ID의 서로 다른 버전 기록 | 거절 | 검사 후 거절 |

정규화한 입력과 전체 출력은 [실행 JSON](records/20261015-workflow-binding-probe.json)에 보존했다. 단일 실행 시간도 기록하지만 성능 순위를 판단할 자료는 아니다. 중복 근거 충돌 검사에는 쌍 비교가 들어가므로 큰 입력의 비용을 별도로 측정해야 한다.

현재 결론은 작은 검사 기능을 구현할 수 있다는 데 그친다. 독립된 두 검토자는 실행 전 코드 검토를 마쳤으며 테스트 파일과 실행 결과는 검토자에게 제공하지 않았다. 코디네이터가 별도로 확인한 항목과 구분한다. 유료 LLM 호출은 없었고 기존 YAGO 실행 결과도 바꾸지 않았다.

등록된 전체 단위 테스트는 261개가 통과했다(`unit-tests`, 종료 코드 0, 83.710초). 이 중 새 검사 모듈의 테스트는 8개다. 소프트웨어 회귀 점검 결과이며 실제 업무 성능을 측정한 수치는 아니다.
