# SHACL 검증 루프 실험 명세

이 실험은 그래프 검색에 SHACL 검증을 더했을 때 잘못된 근거를 얼마나 걸러내는지, 그 대가로 시간과 비용이 얼마나 늘어나는지 확인한다. 현재 단계는 합성 RDF 데이터로 검증기와 채점 절차를 점검하는 사전 점검이다. YAGO와 LLM을 사용한 성능 비교는 후속 실험에서 다룬다.

명세 버전은 0.1이며 작성일은 2026-10-12이다. 조건이나 채점 기준을 바꾸면 버전을 올리고 연구 일지에 이유를 남긴다. 실행 결과를 본 뒤 기준을 바꾼 경우에는 탐색 실험으로 표시한다.

## 연구 질문

같은 질문과 검색 근거에서 검증 루프가 제약 위반 근거의 사용을 줄이는가? 정상 근거를 잘못 차단하는 비율은 어느 정도인가? 재검색을 허용했을 때 답변 정확도와 응답률이 어떻게 달라지는가?

SHACL 통과는 명시한 제약을 만족한다는 뜻이다. 근거의 사실성이나 자연어 답변의 정확성까지 보증하지는 않는다. 답변 품질은 별도 정답과 근거 주석으로 평가한다.

## 진행 단계와 완료 기준

문서에서는 진행 순서를 사전 점검과 1~4단계로 표기한다. 기존 식별자 E0는 사전 점검, E1~E4는 각각 1~4단계에 대응한다. 이번 수정은 단계 명칭만 바꾸며 실험 조건과 채점 기준, 명세 버전 0.1은 유지한다. 과거 실행 ID와 JSON의 `experiment` 값은 추적을 위해 보존한다.

| 단계 | 실행 범위 | 다음 단계로 넘어가는 기준 |
| --- | --- | --- |
| 사전 점검 | 합성 RDF, pySHACL, 위반 주입, 채점, 기록 저장 | 정상 2건과 위반 4건의 판정 및 위반 위치·종류가 기대값과 일치 |
| 1단계 | YAGO 4.6의 작은 슬라이스와 제약 선정 | 배포 파일·라이선스·체크섬 기록, 범위와 누락 처리 기준 확정, 정상 그래프 검증 |
| 2단계 | 고정 질문으로 일반 RAG와 GraphRAG 비교 | 질문·정답·검색 설정·모델·prompt 동결, 비용 예산 확정 |
| 3단계 | 같은 GraphRAG에 검증과 재검색 추가 | 조건별 실행과 실패를 모두 기록, 품질·응답률·지연·토큰 비교 |
| 4단계 | GraphDB 내장 검증과 외부 검증의 배치 비교 | 동일 제약과 추론 설정의 의미가 일치하는지 선행 검증 |

GraphDB Free를 주 실험 엔진으로 사용한다. Neo4j Community 비교와 Neptune 단기 실험은 4단계에서 범위를 정한다. 사전 점검에는 DB나 외부 API가 필요 없다.

## 사전 점검 데이터와 위반 주입

저장소의 `experiments/e0/`에 데이터, shapes, 사례 정의를 둔다. 실제 인물과 관계없는 예제이며 YAGO에서 추출한 데이터가 아니다. 모든 사례는 같은 정상 그래프의 복사본에서 시작한다. 사례를 순서대로 누적 변형하지 않는다.

| 사례 | 조작 | 기대 판정 |
| --- | --- | --- |
| clean | 원본 유지 | 통과 |
| optional_absent | 선택 속성 birthDate 삭제 | 통과 |
| missing_name | 필수 name 삭제 | MinCountConstraintComponent |
| duplicate_name | 두 번째 name 추가 | MaxCountConstraintComponent |
| wrong_datatype | birthDate를 문자열로 교체 | DatatypeConstraintComponent |
| wrong_class | bornIn을 Place가 아닌 Person으로 교체 | ClassConstraintComponent |

사전 점검은 SHACL Core와 명시적 타입만 사용한다. 추론은 `none`, 조기 중단은 끄고 모든 위반을 받는다. 각 사례의 정답은 실행 전에 `cases.json`에 고정한다. 검사기는 기대값을 입력으로 받지 않고 변형한 그래프와 shapes만 검증한다. 채점기는 보고서의 focus node, result path, constraint component를 정답과 대조한다.

사전 점검은 실행 경로와 네 종류 제약을 확인한다. 이 여섯 사례의 검출률을 YAGO나 GraphRAG의 성능으로 일반화하지 않는다.

## 후속 비교 조건

| 조건 | 검색 | 검증 실패 시 동작 |
| --- | --- | --- |
| R0 | 같은 사실을 텍스트로 표현한 일반 RAG | 검증 없음 |
| G0 | GraphRAG | 검증 없음 |
| G1 | G0와 같은 검색 | 실패 근거를 사용하지 않고 답변 보류 |
| G2 | G0와 같은 첫 검색 | 위반 보고서로 최대 2회 재검색, 이후에도 실패하면 보류 |

G1은 검증 자체의 효과, G2는 복구 과정까지 포함한 효과를 관찰한다. G0와 G1은 동일한 검색 결과를 재사용한다. G2의 후속 검색은 별도로 기록한다. 비교군에도 같은 최대 검색 호출 수를 허용한 보조 실험을 두어 추가 연산량의 효과를 구분한다.

검증 대상은 생성 직전의 RDF 근거 그래프다. 질의에 필요한 사실과 타입·관계 검증에 필요한 주변 트리플을 함께 포함한다. 슬라이스 밖으로 잘린 관계를 위반으로 오인하지 않도록 1단계에서 근거 그래프의 포함 범위와 누락 정책을 정한다. 검증 보고서는 내부 재검색에만 전달하고 평가 정답은 모델에 전달하지 않는다.

추론을 도입할 때는 SHACL 검사와 OWL 추론을 별도 조건으로 둔다. 추론 프로파일과 실행 시점, 추가된 트리플을 기록한다. 서로 다른 엔진의 기본 설정을 그대로 비교하지 않는다.

## 측정과 통제

- 사례 단위 검출률은 TP / (TP + FN), 오탐률은 FP / (FP + TN)이다. 분모가 0이면 값을 `null`로 기록한다.
- 위반 위치·종류의 정확 일치는 `(focus node, path, constraint component)` 집합으로 평가한다. 중복 보고서 행은 같은 위반으로 센다.
- 후속 실험의 근거 검증가능률은 유효한 근거 참조가 있고 선언한 제약 검사를 통과한 사실 주장 수 / 전체 사실 주장 수로 정의한다. 사실 주장은 평가용 주석으로 분리한다.
- 답변 정확도는 전체 질문과 응답한 질문을 각각 분모로 보고한다. 보류율과 실패율도 함께 표시해 답변을 많이 포기한 조건이 유리해지지 않도록 한다.
- 검증 시간과 전체 응답 시간을 분리한다. 사전 점검 시간은 단일 호스트의 기능 점검 참고값이다. 성능 비교 전에는 반복 횟수·워밍업·집계 방식을 고정한다.
- 모델 slug, 제공자 라우팅, temperature, prompt 버전, 데이터 체크섬, 질문 목록, 검색량, 컨텍스트 한도, 재시도 횟수를 조건별로 기록한다. OpenRouter의 실제 응답 모델·제공자와 토큰 사용량도 저장한다.

1단계 이후의 표본 수와 API 비용 상한은 파일럿을 보고 본 실험 전에 확정한다. 아직 비용을 발생시키는 반복 실행은 예약하지 않는다. 오류와 timeout을 제외한 숫자만 보고하지 않으며 재실행은 새 run으로 남긴다.

## 실행과 보관

```bash
uv sync --locked
uv run --locked python scripts/run_validation_experiment.py
```

실행마다 `runs/<run-id>/`에 입력 사본과 SHACL 보고서를 저장한다. 공개 가능한 요약과 환경 정보는 `docs/experiments/records/`에 Markdown과 JSON으로 함께 남기며 [실행 기록](records/index.md)에 자동 등록한다. `--local-only`를 지정하면 공개 문서용 파일을 만들지 않는다.

run에는 UTC 시각, Git commit과 미커밋 변경 여부, 코드·데이터·shapes·명세·lockfile의 SHA-256, Python 및 설치 패키지 버전, 사례별 판정과 시간이 들어간다. 환경 변수와 `.env`는 수집하지 않는다. 중단과 예외는 정상 통과로 채점하지 않는다.
