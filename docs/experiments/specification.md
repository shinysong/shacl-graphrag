## 0.5-study1 확대 실행

2026-10-13의 개발 실행을 12개 기업·72개 변형 사례에서 별도 평가 30개 기업·180개 사례까지 확대한다. 개발과 평가를 합쳐 42개 기업이며 기업군 중복 제외와 같은 배포본의 원천 해시는 0.5-dev1의 선정 절차를 유지한다. 180개 사례는 180개의 독립 질문이 아니라 30개 기업에 같은 변형을 적용한 결과다.

### 비교 조건과 반복

| 조건 | 검사와 후속 처리 |
| --- | --- |
| 무검증 `none` | 검사를 생략하고 공통 추출기로 답변 |
| 코드 규칙 `code` | 질문별 계약을 Python으로 검사 |
| SHACL `shacl` | SHACL 보고서를 질문별 통과·위반·확인 불가로 매핑 |
| 무조건 추가조회 `refresh` | 검사 없이 같은 원천을 한 번 더 조회 |
| LLM `llm` | 같은 근거와 계약으로 세 항목을 판정 |
| SHACL+LLM `hybrid` | SHACL의 알려진 위반은 바로 차단하고 나머지는 두 검사 모두 통과해야 답변 |

검사 조건은 확인 불가일 때 같은 원천을 최대 한 번 더 조회한다. 알려진 위반은 바로 보류하며 추가조회 뒤에도 확인 불가면 보류한다. 무조건 추가조회는 이 정책과 다른 대조군이다. 원천에서 얻은 값만 사용하고 평가 정답으로 복구하지 않는다. 최종 답변은 공통 결정적 추출기가 만든다. LLM의 자유로운 문장 생성이나 Text2SPARQL 정확도는 측정하지 않는다.

각 사례·조건을 세 번 반복한다. 실행 순서는 seed 20261013으로 섞고 최대 네 작업을 병렬 처리한다. LLM은 gpt-4o-mini, temperature 0, 출력 최대 240토큰이며 제공자·실제 모델·요청 ID를 보존한다. 모델의 API 자동 재시도는 없다. 개발은 1,296개 결과 행, 평가는 3,240개 결과 행이다.

### 개발 조정과 평가 동결

종류별 첫 개발 기업 하나씩의 12개 사례에서 세 번씩 점검한다. v2의 원시 사실 입력과 v3의 중복 계산 방지·카디널리티 표를 추가한 입력을 비교한다. 기존 v2 구조화 입력도 함께 보존한다. 오류를 불일치로 세고 동등 코드와 첫 종합 판정이 가장 많이 일치한 후보를 선택한다. 동률이면 v2 원시 입력, v3 구조화 입력, 기존 v2 구조화 입력 순이다. 이는 같은 개발 사례를 재사용한 좁은 계약 조정이며 독립적인 프롬프트 성능 평가가 아니다.

전체 개발 실행 뒤 선택한 프롬프트, shapes, 실행 코드, 분석 코드, 설정을 해시로 고정한다. 평가 파일은 미리 보관한 SHA-256과 대조한 뒤 읽는다. 평가 결과를 본 뒤 규칙이나 프롬프트를 고치지 않는다. 실패한 호출과 실행, 실행되지 않은 예정 행도 보존한다.

### 평가 지표와 해석 범위

정답·오답·보류·오류는 전체 결과 행을 분모로 집계한다. 불필요한 보류의 분모는 허용된 원천에서 계약에 맞는 올바른 근거를 얻을 수 있는 행이다. 응답률과 답변 중 오답률도 함께 보고한다. 원천 누락, 검색 누락, 형식에 맞는 거짓 관계 주입을 별도로 분석한다.

주요 차이는 SHACL−코드와 SHACL−LLM의 전체 오답률 및 불필요한 보류율이다. 기업별로 변형과 반복을 먼저 평균한 뒤 기업에 같은 가중치를 준다. 기업 단위 paired bootstrap 10,000회, seed 20261013으로 95% 백분위 구간을 계산한다. 표의 전체 행 집계와 기업 평균의 가중치가 다르므로 구분해서 표시한다. 이번 제한된 실행에서는 p값이나 다중검정의 유의성을 주장하지 않는다. 연구계획의 확증적 검정은 후속 과제로 남긴다. 편의 표본과 인공 변형에 대한 탐색 결과이며 구간이 0이라고 일반적인 동등성을 입증한 것은 아니다.

### 표현 비교와 별도 모델 점검

Neo4j Community의 실제 Cypher 질의를 개발 72개 사례의 RDF/SPARQL 결과와 대조한다. 노드 라벨·관계·속성으로 적재하고 리터럴 datatype과 언어 태그를 보존한다. 같은 검색 근거가 나오는지 확인하는 절차이며 엔진 속도 벤치마크가 아니다. 임시 로컬 컨테이너는 점검 뒤 종료한다.

Jev는 별도 개발 스모크로 실행한다. OpenRouter Decisions API의 `typesafe/jev-1.13`을 사용해 항목별 선택 확률의 최댓값으로 판정한다. 12개 사례·3회 반복, 최대 72회·예약액 $0.20이며 주 평가 비교에는 포함하지 않는다. 확률 보정이나 LLM 대비 우위는 주장하지 않는다.

첫 Jev 점검 뒤 개발 전체로 확대한 `0.5-jev-dev-full1`을 별도 실행했다. 개발 12개 기업·72개 사례·3회 반복의 216개 결과이며 최대 432회·예약액 $1을 허용한다. 전체 작업의 공유 상한 3,200회·$5는 유지한다. 주 평가의 여섯 조건이나 동결된 분석을 바꾸지 않고 Jev의 별도 평가·확률 보정·일반적 동등성을 주장하지 않는다.

이번 확대 작업 전체의 API 상한은 실패를 포함해 3,200회·예약액 $5다. 전송 전에 공유 장부에 예약하고 반환하지 않는다. 개별 실행에도 상한을 두며 누락된 비용이나 예약액 초과 응답은 후속 호출을 중단한다. AWS와 Codex 비용은 이 금액에 포함하지 않는다.

## 0.5-dev1 개발 실행 범위

2026-10-13에 새 연구계획의 개발 실행을 시작한다. 아래 조건은 GLEIF 개발 집합에만 적용하며 기존 0.4 파일럿을 대체하지 않는다. YAGO·Neo4j/Cypher·Jev·결합 조건과 최종 평가 실행은 아직 포함하지 않는다.

- 원천: 2026-10-12 08:00 GLEIF LEI/RR/REPEX Golden Copy. 세 파일의 SHA-256과 전체 행 수를 재검증한다.
- 표본: 직접 모회사와 보고 예외 각각 21개, 총 42개 중심 법인. 종류별 6개씩 개발 12개, 15개씩 평가 후보 30개를 분리한다. 각각 최초 10,000개 발견 후보 안에서 seed 20261013의 SHA-256 순위로 선택한다. 편의 표본이며 대표성을 주장하지 않는다.
- 중복 제외: 전체 ACTIVE/PUBLISHED 직접·최종 회계 연결 관계의 무방향 연결 성분을 사용한다. 기존 파일럿 법인·모회사와 연결된 기업군을 제외하고 기업군당 중심 법인 하나만 선택한다. 평가 후보의 정답 파일은 개발 실행기에 전달하지 않는다.
- 질문: 직접 회계 연결 모회사 또는 해당 보고 예외 코드 하나. 법인명은 권고 정보이며 답변 차단에 사용하지 않는다. 올바른 보고 예외는 완전한 답변이다.
- 변형: 모회사 7종, 예외 5종으로 총 72개 개발 사례. 정상·무관한 이름 누락·검색 누락·원천 누락·명시적 타입 위반·허용되지 않은 예외 코드·형식에 맞는 다른 모회사 치환을 구분한다. 변형은 서로 독립적으로 주입한다.
- 결정적 비교: 무검증·동등 코드·SHACL과 질문별 정책·무조건 1회 재조회. 확인 불가만 같은 원천에서 최대 1회 재조회하고 알려진 위반은 바로 보류한다. 공통 추출기는 후보가 없거나 복수면 보류한다. SHACL 원시 보고서와 공통 판정 매핑을 함께 저장한다.
- 표현 점검: RDF/SPARQL 결과와 메모리의 LPG 참조 표현을 공통 사실 목록으로 대조한다. 식별자·리터럴 datatype·언어 태그를 보존한다. 이 LPG 경로는 Cypher나 Neo4j 실행이 아니므로 엔진 성능 비교로 해석하지 않는다.
- 모델 스모크: 종류별 첫 개발 법인 하나의 12개 사례만 별도 실행한다. 같은 사실과 검사 기준으로 항목별·종합 판정을 받고 결정적 추출기로 답변한다. gpt-4o-mini 요청, temperature 0, 1회 반복, 자동 재시도 없음. 최대 24회·예약액 $0.10, 제공자 토큰 단가 상한은 입력 $0.20/백만·출력 $0.80/백만이다. 매 전송 전에 호출 수와 예약액을 저장한다. 실패도 기록하며 모델의 요청 ID·실제 모델·제공자·사용량을 보존한다.
- 평가: 주입 전 GLEIF 스냅샷 값을 평가자만 정답으로 사용한다. 외부 진실 검증이 아니다. 오답·보류·실패를 전체 사례 분모에 남기며 불필요한 보류의 분모는 허용 원천에서 올바른 계약 근거를 얻을 수 있는 사례다. 개발 결과에 유의성·일반화·동등성 주장을 붙이지 않는다.

설정과 구현은 `experiments/comparison/` 및 `scripts/run_gleif_comparison.py`에 보관한다. 평가 후보 30개는 표본 규모·검정 방법·최종 질의·모델 조건·예산을 확정하기 전까지 실행하지 않는다. 전체 계획의 3회 모델 반복과 생성 모델 비교는 이 스모크의 완료 기준이 아니다.

## 기존 0.4 실행 명세

새 비교 설계는 [RDF와 SHACL 기반 질의응답 연구계획서](research-plan.md)에 정리했다. 아래 명세 0.4는 기존 실행을 재현하는 기준으로 유지한다.

이 실험은 그래프 검색에 SHACL 검증을 더했을 때 잘못된 근거를 얼마나 걸러내는지, 그 대가로 시간과 비용이 얼마나 늘어나는지 확인한다. 합성 RDF 사전 점검에 이어 GLEIF Golden Copy로 작은 실제 데이터 파일럿을 진행한다. GLEIF에 이어 YAGO 4.6의 원본 SHACL로 후속 파일럿을 진행한다.

이하의 기존 실행 명세 버전은 0.4이며 작성일은 2026-10-12이다. 조건이나 채점 기준을 바꾸면 버전을 올리고 연구 일지에 이유를 남긴다. 실행 결과를 본 뒤 기준을 바꾼 경우에는 탐색 실험으로 표시한다.

## 연구 질문

같은 질문과 검색 근거에서 검증 루프가 제약 위반 근거의 사용을 줄이는가? 정상 근거를 잘못 차단하는 비율은 어느 정도인가? 재검색을 허용했을 때 답변 정확도와 응답률이 어떻게 달라지는가?

SHACL 통과는 명시한 제약을 만족한다는 뜻이다. 근거의 사실성이나 자연어 답변의 정확성까지 보증하지는 않는다. 답변 품질은 별도 정답과 근거 주석으로 평가한다.

| 사전 점검 | 합성 RDF, pySHACL, 위반 주입, 채점, 기록 저장 | 정상 2건과 위반 4건의 판정 및 위반 위치·종류가 기대값과 일치 |
| 1단계 | GLEIF 동일 시점 배치 3종과 작은 부분집합·제약 선정 | 배포 파일·라이선스·체크섬 기록, 범위와 누락 처리 기준 확정, 정상 그래프 검증 |
| 2단계 | 고정 질문으로 일반 RAG와 GraphRAG 비교 | 질문·정답·검색 설정·모델·prompt 동결, 비용 예산 확정 |
| 3단계 | 같은 GraphRAG에 검증과 재검색 추가 | 조건별 실행과 실패를 모두 기록, 품질·응답률·지연·토큰 비교 |
| 4단계 | GraphDB 내장 검증과 외부 검증의 배치 비교 | 동일 제약과 추론 설정의 의미가 일치하는지 선행 검증 |

본 실험의 주 엔진 계획은 GraphDB Free다. 이번 파일럿은 RDFLib의 메모리 그래프와 외부 pySHACL로 실행하며 GraphDB 성능을 측정하지 않는다. Neo4j Community 비교와 Neptune 단기 실험은 4단계에서 범위를 정한다. 사전 점검에는 DB나 외부 API가 필요 없다.

## 사전 점검 데이터와 위반 주입

저장소의 `experiments/e0/`에 데이터, shapes, 사례 정의를 둔다. 실제 인물과 관계없는 예제이며 YAGO에서 추출한 데이터가 아니다. 모든 사례는 같은 정상 그래프의 복사본에서 시작한다. 사례를 순서대로 누적 변형하지 않는다.

| 사례 | 조작 | 기대 판정 |
| --- | --- | --- |
| clean | 원본 유지 | 통과 |
| optional_absent | 선택 속성 birthDate 삭제 | 통과 |
| missing_name | 필수 name 삭제 | MinCountConstraintComponent |
| duplicate_name | 두 번째 name 추가 | MaxCountConstraintComponent |
| wrong_datatype | birthDate를 문자열로 교체 | DatatypeConstraintComponent |
| wrong_class | bornIn을 Place가 아닌 Person으로 교체 | ClassConstraintComponent |

사전 점검은 SHACL Core와 명시적 타입만 사용한다. 추론은 `none`, 조기 중단은 끄고 모든 위반을 받는다. 각 사례의 정답은 실행 전에 `cases.json`에 고정한다. 검사기는 기대값을 입력으로 받지 않고 변형한 그래프와 shapes만 검증한다. 채점기는 보고서의 focus node, result path, constraint component를 정답과 대조한다.

사전 점검은 실행 경로와 네 종류 제약을 확인한다. 이 여섯 사례의 검출률을 GLEIF나 GraphRAG의 성능으로 일반화하지 않는다.

## 후속 비교 조건

| 조건 | 검색 | 검증 실패 시 동작 |
| --- | --- | --- |
| R0 | 같은 사실을 텍스트로 표현한 일반 RAG | 검증 없음 |
| G0 | GraphRAG | 검증 없음 |
| G1 | G0와 같은 검색 | 실패 근거를 사용하지 않고 답변 보류 |
| G2 | G0와 같은 첫 검색 | 위반 보고서로 최대 2회 재검색, 이후에도 실패하면 보류 |

G1은 검증 자체의 효과, G2는 복구 과정까지 포함한 효과를 관찰한다. G0와 G1은 동일한 검색 결과를 재사용한다. G2의 후속 검색은 별도로 기록한다. 비교군에도 같은 최대 검색 호출 수를 허용한 보조 실험을 두어 추가 연산량의 효과를 구분한다.

검증 대상은 생성 직전의 RDF 근거 그래프다. 질의에 필요한 사실과 타입·관계 검증에 필요한 주변 트리플을 함께 포함한다. 슬라이스 밖으로 잘린 관계를 위반으로 오인하지 않도록 1단계에서 근거 그래프의 포함 범위와 누락 정책을 정한다. 검증 보고서는 내부 재검색에만 전달하고 평가 정답은 모델에 전달하지 않는다.

추론을 도입할 때는 SHACL 검사와 OWL 추론을 별도 조건으로 둔다. 추론 프로파일과 실행 시점, 추가된 트리플을 기록한다. 서로 다른 엔진의 기본 설정을 그대로 비교하지 않는다.

## GLEIF 파일럿 고정 조건

2026-10-12 08:00:00 배포의 Golden Copy CSV 세 종류(법인 LEI, 관계 RR, 보고 예외 REPEX)를 사용한다. 원본 압축 파일과 배포 메타데이터, 다운로드 시각, SHA-256을 보관한다. 데이터는 [GLEIF CC0 이용 조건](https://www.gleif.org/en/meta/lei-data-terms-of-use/)을 따른다. API 예시와 배치 데이터의 JSON 구조가 같다고 가정하지 않는다.

전체 CSV를 읽고 두 집단에서 법인을 각각 네 개 선정한다. 한 집단은 활성 직접 회계연결 관계가 하나이며 보고 예외가 없는 법인이고 다른 집단은 직접 모회사 보고 예외가 하나인 법인이다. 법인과 모회사는 ACTIVE·ISSUED, 관계는 ACTIVE·PUBLISHED인 범위로 좁힌다. CSV 등장 순서에 따른 편의 표본이며 대표성을 주장하지 않는다. 각 집단의 첫 법인은 개발용으로 분리하고 나머지 세 개씩을 파일럿에 사용한다. 선택한 법인의 관련 관계·예외와 모회사 레코드를 보존한다. 모든 원본 행 수를 배포 메타데이터와 대조한다.

질문은 법인의 직접 회계연결 모회사 또는 보고 예외 코드를 묻는 단일 홉 질의다. 법인 연결은 LEI가 주어진 상태에서 시작한다. Text2SPARQL과 개체 연결 정확도는 측정하지 않는다. RDFLib의 고정 CONSTRUCT 질의로 근거를 검색한다. R0는 같은 근거를 텍스트로 직렬화한 비교군이며 독립적인 벡터 검색 RAG가 아니다.

| 사례 | 변형 위치 | 검증 기대값 |
| --- | --- | --- |
| clean | 원본 유지 | 통과 |
| missing_name | 검색 근거에서 법인명 제외 | 위반, 재검색으로 복구 가능 |
| missing_relation | 검색 근거에서 모회사 관계 제외 | 위반, 재검색으로 복구 가능 |
| missing_exception | 검색 근거에서 보고 예외 제외 | 위반, 재검색으로 복구 가능 |
| invalid_lei | 사례별 원천 그래프의 모회사 LEI를 잘못된 형식으로 변경 | 위반, 같은 원천 재검색으로 복구 불가 |
| invalid_reason | 사례별 원천 그래프의 보고 예외를 미정의 코드로 변경 | 위반, 같은 원천 재검색으로 복구 불가 |
| wrong_parent | 사례별 원천 그래프에서 다른 정상 법인을 모회사로 연결 | 제약은 통과하지만 스냅샷 정답과 불일치 |

모회사 법인은 다섯 사례, 예외 법인은 세 사례를 구성해 파일럿은 총 24건이다. 원본마다 독립 복사하고 변형을 누적하지 않는다. 마지막 세 사례는 주입한 오류로서 실제 GLEIF 오류로 보고하지 않는다. SHACL 규칙은 제한된 근거 계약이며 GLEIF 공식 품질 규칙 전체를 구현한 것이 아니다. LEI 검사는 문자열 패턴만 확인하며 체크섬 검사는 포함하지 않는다. 법인명 필수 조건은 질의 자체에 필요한 최소 근거보다 강하므로 과도한 차단 가능성을 따로 해석한다.

G0와 G1은 바이트 단위로 같은 첫 근거를 쓴다. G2는 SHACL 보고서의 focus node와 path를 바탕으로 누락 속성이나 관계 주변을 같은 원천 그래프에서 최대 두 번 다시 조회한다. 주입 전 정답 그래프는 재검색에 제공하지 않는다. 추가 비교 U2는 위반 보고서를 보지 않고 전체 근거를 한 번 다시 조회한다. 두 조건의 상한은 같은 두 번이며 실제 호출 수와 검색 트리플 수를 기록한다. P1은 같은 조건을 Python으로 검사한 뒤 위반이면 보류한다. Python과 SHACL의 판정 일치율도 측정한다.

LLM은 .env의 OpenRouter 모델을 사용하고 temperature 0, 출력 상한 240 tokens로 고정한다. 답은 parent LEI 또는 exception code와 근거 ID를 담은 JSON으로 제한한다. 평가 정답과 사례 이름은 모델에 보내지 않는다. 최대 160회, 비용 예산 1 USD, 제공자 가격 상한은 입력 0.2 USD/백만 tokens·출력 0.8 USD/백만 tokens다. 매 호출 전에 보수적 입력 문자 수로 비용 여유를 확인하고 사용량을 기록한다. 자동 네트워크 재시도는 하지 않는다. 제한 도달·API 오류·파싱 오류는 보류와 구분해 저장한다.

조건 실행 순서는 seed 20261012로 섞고 사례당 한 번 실행한다. 별도 워밍업이나 유의성 검정은 하지 않는다. 결과는 탐색 파일럿이며 본 실험 전에 표본·반복·질문 난도를 다시 확정한다. 답변 정확도는 주입 전 스냅샷에서 만든 구조화 정답의 정확 일치로 계산한다. 답변 근거 지지는 인용 ID의 존재뿐 아니라 해당 관계와 LEI 또는 예외 코드가 실제 근거에 있는지 확인한다. 현실의 최신 사실에 대한 독립 감사나 자유 서술 환각 평가는 아니다.

```text
고정 배치 3종 → 표본·원본 보존 → 사례별 원천 / 검색 누락 분리
                                      ↓
                          동일 첫 근거 → 조건별 검사·재검색
                                      ↓
                          LLM 구조화 답변 → 별도 정답 채점
```

## 측정과 통제

- 사례 단위 검출률은 TP / (TP + FN), 오탐률은 FP / (FP + TN)이다. 분모가 0이면 값을 `null`로 기록한다.
- 위반 위치·종류의 정확 일치는 `(focus node, path, constraint component)` 집합으로 평가한다. 중복 보고서 행은 같은 위반으로 센다.
- 후속 실험의 근거 검증가능률은 유효한 근거 참조가 있고 선언한 제약 검사를 통과한 사실 주장 수 / 전체 사실 주장 수로 정의한다. 사실 주장은 평가용 주석으로 분리한다.
- 답변 정확도는 전체 질문과 응답한 질문을 각각 분모로 보고한다. 보류율과 실패율도 함께 표시해 답변을 많이 포기한 조건이 유리해지지 않도록 한다.
- 검증 시간과 전체 응답 시간을 분리한다. 사전 점검 시간은 단일 호스트의 기능 점검 참고값이다. 성능 비교 전에는 반복 횟수·워밍업·집계 방식을 고정한다.
- 모델 slug, 제공자 라우팅, temperature, prompt 버전, 데이터 체크섬, 질문 목록, 검색량, 컨텍스트 한도, 재시도 횟수를 조건별로 기록한다. OpenRouter의 실제 응답 모델·제공자와 토큰 사용량도 저장한다.

이번 파일럿의 표본과 예산은 위 조건으로 고정한다. 본 실험의 표본 수와 반복 횟수는 파일럿 이후 별도로 확정한다. 오류와 timeout을 제외한 숫자만 보고하지 않으며 재실행은 새 run으로 남긴다.

## YAGO 원본 SHACL 후속 파일럿 — 명세 0.3

GLEIF 명세 0.2와 측정값은 유지하고 YAGO 4.6을 두 번째 파일럿으로 추가한다. [공식 배포](https://yago-knowledge.org/downloads/yago-4-6)의 schema와 tiny 파일을 고정하며 CC BY 4.0 출처를 표시한다. 전체 YAGO 사실을 적재한 실험은 아니다.

원본 schema.ttl은 바이트를 변경하지 않는다. 전체 55개 NodeShape와 5,536개 트리플을 pySHACL에 전달하고 전체 검사를 수행한 뒤 질의 인물과 근거의 출생지 노드에 해당하는 최상위 결과만 추린다. pySHACL의 focus_nodes 옵션은 중첩된 리터럴 검사를 누락시켜 사용하지 않는다. shape 선택을 강제로 지정하지 않고 원본의 클래스 타깃을 사용한다. 원본 하위 클래스 경로와 그 경로가 뜻하는 클래스 선언을 별도 taxonomy.ttl로 제공한다. OWL 추론, rdfs:range에 의한 대상 타입 보정은 하지 않는다. 재검색도 사례별 원천만 읽는다.

공식 tiny 파일의 birthPlace 등장 순서에서 출생지·생년월일·이름·타입 경로가 있는 첫 네 인물을 선정한다. 첫 인물은 개발용, 나머지 세 인물은 파일럿에 사용한다. 대상 인물만 분리하며 연결 장소나 교란 대상으로 사용한 노드의 완전한 분리를 주장하지 않는다. 생년월일은 질문의 정답이 아니지만 원본 Person shape가 검사하는 주변 근거로 포함한다.

| 사례 | 변형 위치 | 원본 SHACL 기대값 |
| --- | --- | --- |
| clean | 원본 유지 | 통과 |
| missing_label | 검색에서 인물 이름 제외 | minCount 위반 |
| missing_relation | 검색에서 출생지 관계 제외 | 통과: birthPlace에 minCount 없음 |
| missing_target_type | 검색에서 출생지 노드 타입 제외 | class 위반 |
| duplicate_relation | 사례별 원천에 두 번째 정상 장소 추가 | maxCount 위반 |
| wrong_class | 사례별 원천의 출생지를 다른 Person으로 교체 | class 위반 |
| wrong_datatype | 사례별 원천의 생년월일을 xsd:string으로 교체 | or 자료형 위반 |
| wrong_place | 사례별 원천의 출생지를 다른 정상 Place로 교체 | 통과: 사실 오류는 별도 정답으로 확인 |

총 24개 사례에 R0/G0/G1/G2/U2/P1을 적용한다. R0는 같은 근거의 텍스트 표현이며 벡터 검색 비교가 아니다. P1은 이 부분집합에 등장하는 제약의 Python 구현이며 전체 YAGO 스키마를 구현한 검사기는 아니다. 원본과의 판정 일치를 사례별로 기록한다. G2는 위반이 있을 때만 최대 두 번 재검색한다. 따라서 제약을 통과하는 missing_relation은 재검색하지 않는다. U2는 위반과 관계없이 전체 근거를 한 번 다시 조회한다.

질문에는 인물 URI가 주어지며 고정 CONSTRUCT 질의를 사용한다. 답은 출생지 URI와 인용 ID로 제한하고 원본 부분집합의 값과 정확 일치로 채점한다. GLEIF와 모델·temperature·예산·조건의 큰 구조는 맞추지만 질문·원천 제약·prompt가 다르므로 두 데이터셋의 정답률 차이를 데이터셋 우열로 해석하지 않는다. 사례당 1회 실행하며 대표성·유의성을 주장하지 않는다.

LLM은 기존 OpenRouter 설정을 사용한다. 실행당 최대 160회, 예산 1 USD, 출력 240 tokens, temperature 0, seed 20261012의 조건 순서를 사용한다. 모델·제공자·토큰·비용과 오류를 저장한다. 정답은 생성과 재검색에 전달하지 않는다. 조건별 시간은 공유된 첫 검색과 배치 전처리를 제외한다.

```bash
uv run --locked python scripts/download_yago.py
uv run --locked python scripts/prepare_yago.py
uv run --locked python scripts/run_yago_pilot.py --split development --validate-only
uv run --locked python scripts/run_yago_pilot.py
```

## 질의 관련성·근거 충분성 후속 실험 — 명세 0.4

원본 데이터와 SHACL을 유지하고 답변 차단 정책만 비교한다. 명세 0.3의 결과를 보고 설계한 탐색 실험이며 같은 인물을 재사용하므로 독립적인 확인 실험은 아니다. LLM 실행 전에 아래 조건을 고정한다.

| 조건 | 검사와 처리 |
| --- | --- |
| G0 · 검증 없음 | 첫 근거로 바로 답변 |
| G1 · 일괄 차단 | 원본 SHACL 위반이면 보류 |
| G2 · 일괄 차단 후 재검색 | 원본 위반을 기준으로 재검색 후 재검사 |
| U2 · 무조건 재조회 | 검사 결과와 관계없이 한 번 재조회 |
| S1 · 선택적 차단 | 질의 인물의 birthPlace 위반만 차단; 다른 위반은 기록 |
| S2 · 선택적 차단과 누락 보완 | S1에 출생지 관계의 존재·유일성 검사를 추가하고 불충분하면 재검색 |
| C2 · 충분성 검사와 재검색 | 출생지 관계가 정확히 하나인지 확인하고 재검색; SHACL 판정은 차단에 사용하지 않음 |

질문은 출생지 URI 질의로 고정한다. 관련성은 사전에 정한 `(질의 인물, schema:birthPlace)` 경로로 결정한다. 라벨·출생일 오류는 답변을 막지 않는다. 이는 이 질문에 한정된 계약이며 임의 질문의 관련성을 자동 판단하는 모델은 아니다. 모든 정책은 실제 근거와 보고서만 읽고 사례 이름·정답은 읽지 않는다. 원본 SHACL에는 제약을 추가하지 않는다.

원본 표본의 기존 8개 상태에 `source_missing_relation`을 추가한다. 이 상태는 사례별 원천에서 출생지 관계를 제거한다. 검색 누락과 달리 재검색으로도 복구할 수 없다. 원천에 정보가 없다는 뜻이며 현실에서 출생지가 없다는 뜻은 아니다. 개발 1명 × 9개 상태, 파일럿 3명 × 9개 상태에 7개 조건을 적용한다. 기존 0.3 결과는 보존하고 비교군도 새 실행에서 다시 측정한다.

재검색은 같은 사례의 원천만 최대 두 번 읽는다. S2/C2는 관계가 없거나 둘 이상이면 다시 조회한다. S2는 관련 SHACL 위반도 재검색하며 변화가 없으면 중단한다. S1은 재검색하지 않는다. SHACL 전체 검사는 감사 기록을 위해 S1/S2/C2에서도 수행하지만 C2의 차단에는 사용하지 않는다. 따라서 C2 실행 시간을 SHACL 없는 엔진의 성능으로 해석하지 않는다.

정답 수·오답 수·보류 수·오류를 함께 기록한다. 정답은 주입 전 스냅샷과의 일치이며 `source_missing_relation`에는 생성용 정답을 두지 않고 보류를 따로 집계한다. 불필요한 보류의 분모에는 원천에서 모호하지 않은 올바른 출생지를 확인할 수 있는 사례를 넣는다. 5개 상태(clean, missing_label, missing_relation, missing_target_type, wrong_datatype)가 이에 해당하며 파일럿에서는 15개 사례다. 충돌·잘못된 클래스·사실 오류·원천 누락은 이 분모에서 제외한다. 사실 오류는 별도 정답과 비교하며 새 정책으로 해결된다고 가정하지 않는다.

모델·prompt·temperature·가격 상한은 0.3과 같다. 실행당 최대 220회, 예산 1 USD, 조건 순서 seed 20261012, 사례당 1회다. 현재 표본에서 가설을 다듬은 결과로서 일반화나 통계적 우열을 주장하지 않는다.

```bash
uv run --locked python scripts/run_yago_selective.py --split development --validate-only
uv run --locked python scripts/run_yago_selective.py
```
