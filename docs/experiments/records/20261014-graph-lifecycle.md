# 2026-10-14 — JSON과 Neo4j의 변경 반영 비교

실행 `20261014T015328Z-graph-lifecycle`에서 합성 공급망의 세 비교군을 실제로 실행했다. 예정된 2,880행이 모두 완료됐으며 실행 오류와 미실행 행은 0개다. [실험계획](../graph-lifecycle-study.md)의 동일한 데이터·변경 이력·역할 규칙을 사용했다. OpenRouter와 다른 모델 API는 호출하지 않았다.

## 답과 경로 근거

| 비교군 | 답과 전체 경로 일치 | 반복 조회의 불일치 |
| --- | --- | --- |
| JSON 관계 목록 탐색 | 960 / 960 | 0 |
| JSON 인덱스 | 960 / 960 | 0 |
| 실제 Neo4j Cypher | 960 / 960 | 0 |

제품 100·1,000·5,000개로 시작해 두 시드와 여덟 변경 지점을 사용했다. 각 지점에서 기존 제품 18개, 추가될 제품 하나, 존재하지 않는 ID 하나를 질의했다. 제품 추가 지점에서는 초기 제품 수의 10%를 더했다. 따라서 가장 큰 조건의 후반에는 제품 5,500개가 있다. 이 결과는 실제 기업 표본이나 LLM 답변 정확도가 아니라 합성 스냅샷의 국가 집합과 관계 경로를 대조한 값이다.

변경 전후를 짝지으면 비교군마다 답 또는 경로가 바뀌어야 하는 경우 63개와 그대로여야 하는 경우 777개가 있었다. 두 범주 모두 기대 결과와 일치했다. 이는 840개의 변경 전후 대응이며 독립적인 업무 표본이 아니다.

## 실제 변경 사례

질문은 “허용된 공급자 역할을 따라 제품에서 도달하는 국가는 어디이며, 근거 경로는 무엇인가”로 고정했다. 아래 ID는 합성 데이터이며 실제 기업·지역을 뜻하지 않는다. 세 비교군은 모두 같은 결과를 냈다.

| 대상과 변경 | 변경 전 | 변경 후 | 판단 근거 |
| --- | --- | --- | --- |
| p0의 공급자 s0 지역 변경 | c0 | c1 | `p0 → s0 → r1 → c1`로 경로 갱신 |
| p2 공급 관계 삭제 | c1 | 빈 집합 | 제품에서 공급자로 가는 관계가 없어 경로 단절 |
| p2 공급 관계 복구 | 빈 집합 | c1 | 기존 공급 관계를 복구해 경로 재성립 |
| p3 예비 관계 추가, 아직 허용 안 함 | c1 | c1 | backup 역할이 현재 규칙 밖에 있음 |
| p3 예비 공급자 허용 | c1 | c1, c2 | `p3 → s2 → r2 → c2` 경로 추가 |
| p3 허용 규칙 복원 | c1, c2 | c1 | 예비 관계는 남지만 질의 규칙에서 제외 |
| new0 제품 추가 | 빈 집합 | c0 | 새 제품과 공급 관계가 함께 생성됨 |
| p17, 영향 없는 대조 제품 | c1 | c1 | 다른 공급자의 경로 유지 |

빈 집합은 현재 정보와 규칙으로 뒷받침되는 경로가 없다는 뜻이다. 현실에 공급자가 없다고 판정하거나 LLM이 답변을 보류한 결과가 아니다. [원시 사례](20261014-graph-lifecycle-samples.json)에는 국가뿐 아니라 공급·지역·국가 관계 ID와 실제 Cypher 반환 경로를 보존했다.

## 조회 시간

각 행에서 한 번 예열하고 세 번 측정했다. 각 행의 세 측정에서 중앙값을 구한 뒤 조건별로 다시 중앙값을 계산했다. 아래 표의 단위는 ms다. 총 조회 호출은 예열을 포함해 11,520회다. 독립된 질문 11,520개를 의미하지 않는다.

| 초기 제품 수 | JSON 목록 탐색 | JSON 인덱스 | Neo4j HTTP |
| --- | ---: | ---: | ---: |
| 100 | 0.0540 | 0.0387 | 5.2691 |
| 1,000 | 0.1550 | 0.0418 | 3.7583 |
| 5,000 | 0.6039 | 0.0415 | 3.2118 |

이 조건에서는 메모리의 JSON 인덱스 조회가 가장 빨랐다. Neo4j는 localhost HTTP 통신과 응답 처리를 포함하고 JSON은 같은 Python 프로세스 안에서 조회하므로 저장 엔진 자체의 성능 비교는 아니다. 규모와 비교군 순서가 고정돼 있어 뒤 조건의 Neo4j 시간이 줄어든 현상을 규모 증가의 효과로 해석할 수 없다. 캐시·쿼리 컴파일·실행 순서의 영향을 분리하지 않았다.

## 변경 적용 시간

초기 제품 5,000개 조건의 두 반복 중앙값이며 단위는 ms다. 아래 값에는 공통 규칙 파일 저장 시간을 넣지 않았다. 규칙 파일 저장은 모든 비교군이 공유하는 별도 작업으로 기록했다.

| 변경 | JSON 목록 탐색 | JSON 인덱스 | Neo4j HTTP |
| --- | ---: | ---: | ---: |
| 초기 적재 | 111.911 | 117.308 | 678.803 |
| 제품 500개 추가 | 89.737 | 91.394 | 93.897 |
| 공급자 지역 변경 | 88.458 | 89.475 | 76.383 |
| 공급 관계 하나 삭제 | 87.896 | 92.983 | 16.703 |
| 공급 관계 하나 복구 | 87.369 | 91.905 | 31.408 |
| 예비 공급 관계 하나 추가 | 86.954 | 89.163 | 7.966 |

JSON은 그래프 변경 때 파일 전체를 직렬화·fsync·교체하고 인덱스 조건은 인덱스도 다시 만든다. Neo4j는 해당 노드·관계의 변경만 트랜잭션으로 전달한다. 일부 작은 변경에서 Neo4j 경로가 더 짧았지만 이는 이 JSON 저장 정책과 비교한 결과다. 로그 기반 JSON 저장이나 다른 증분 저장 구현까지 이겼다는 뜻은 아니다. 규칙만 바꿀 때는 세 조건 모두 그래프를 다시 저장하지 않고 설정을 질의에 전달했다.

## 환경과 검증

Python 3.12.3, httpx 0.28.1, Neo4j Community 5.26.32를 사용했다. 기존 서버의 캐시된 컨테이너를 localhost에만 열고 메모리 3GiB·CPU 2개로 제한했다. 클라이언트 실행은 101.96초였으며 최대 RSS는 74,428KiB였다. 이 RSS는 DB 컨테이너 메모리를 포함하지 않는다. 종료 직전 컨테이너 표본은 884.5MiB였으며 최대치 측정은 아니다. 컨테이너와 실험 데이터는 종료 후 제거했다.

독립 검토에서 발견한 대조 누락 가능성을 수정하고 새 검토 두 건과 소프트웨어 테스트 155개를 통과한 뒤 실행했다. 모든 예정 행, 스냅샷, 소스 해시, 변경량과 시간 및 부분 조회 기록은 원본 실행 폴더에 남겼다. [검증 보강 기록](../../lessons-learned/2026-10-14-lifecycle-coverage.md)도 보존했다.

독립 SPARQL 대조의 첫 시도는 느린 조합 탐색 때문에 322개 질의·966행까지 확인한 뒤 중단했다. 부분 결과와 실패 상태를 보존하고, 관계 경로별로 질의 구간을 나눈 검증기로 별도 검토를 거쳤다. 본 실험의 DB 실행과 측정값은 변경하지 않았다.

새 검증기로 48개 스냅샷·960개 질의·2,880행 전체를 대조했고, 국가 집합과 경로 근거의 불일치는 0개였다. RDFLib 7.6.0의 메모리 SPARQL 실행이며 RDF DB 성능 측정은 아니다. 스냅샷의 외부 사실 진위를 확인한 결과도 아니다.
