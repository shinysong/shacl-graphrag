# 제조·의료·금융·전자상거래 데모 구성과 검사 결과

네 도메인에 각각 업무 데이터 200행과 참조 테이블 두 개를 만들고 규칙 검토 도구가 실제로 어떻게 처리하는지 확인했다. 업무 데이터는 총 800행이며 제품·환자·계정·고객 등의 참조 데이터를 더하면 **1,020행**이다.

공개 자료의 스키마를 참고했지만 레코드는 모두 이번 테스트를 위해 만든 합성 데이터다. 실제 기업이나 환자의 기록을 가져온 것은 아니다. 필수값, 범위, 허용값, 날짜 순서, 다른 표의 값 참조라는 다섯 가지 검사 유형을 서로 다른 도메인과 파일 형식에 적용했다.

## 도메인별 데이터와 참고 자료

| 도메인 | 업무 테이블 | 참조 테이블 | 전체 행 |
|---|---|---|---:|
| 제조 | 작업지시 `WorkOrders` 200행 | 제품 `Products` 24행, 공정 `Routing` 24행 | 248 |
| 의료 | 진료기록 `Encounters` 200행 | 환자 `Patients` 40행, 의료진 `Practitioners` 12행 | 252 |
| 금융 | 지급 `Payments` 200행 | 계정 `Accounts` 20행, 거래상대방 `Counterparties` 30행 | 250 |
| 전자상거래 | 주문 `Orders` 200행 | 고객 `Customers` 40행, 상품 `Products` 30행 | 270 |

제조 데이터는 [Microsoft AdventureWorks](https://learn.microsoft.com/en-us/sql/samples/adventureworks-install-configure?view=sql-server-ver17)를 참고해 작업지시가 제품과 공정을 참조하도록 구성했다. 의료 데이터는 [HL7 FHIR R4 Encounter](https://hl7.org/fhir/R4/encounter.html)의 진료·환자·의료진 관계를 단순한 표로 옮겼다. 이 표 자체가 FHIR 리소스이거나 FHIR 적합성 검사를 통과한 데이터라는 뜻은 아니다.

금융 데이터는 [Stripe PaymentIntent](https://docs.stripe.com/api/payment_intents/object)를 참고하되 지급·계정·거래상대방을 연결하는 별도 구조로 만들었다. 금액은 최소 화폐 단위로 표현했고 지급 상태와 금액 한도는 데모용으로 정했다. 전자상거래는 도매업 예제인 [Microsoft WideWorldImporters](https://github.com/microsoft/sql-server-samples/blob/master/samples/databases/wide-world-importers/README.md)를 참고해 주문 항목이 고객과 상품을 참조하는 구조로 단순화했다.

식별자, 이름, 거래, 규칙의 한도는 모두 직접 작성했다. 특히 의료 데이터의 숫자 검사는 행정용 순번을 대상으로 하며 임상적 정상 범위를 판단하지 않는다. 네 도메인이 공통 검사 유형을 공유하므로 이번 결과만으로 실제 의료·금융 업무 정확성이나 도메인 간 일반화 성능을 주장할 수는 없다.

```text
작업지시 ── product_id ──→ 제품       진료기록 ── patient_id ──→ 환자
   │                                    │
 routing_id                        practitioner_id
   ↓                                    ↓
  공정                                 의료진

 지급 ── account_id ──→ 계정           주문 ── customer_id ──→ 고객
   │                                    │
 counterparty_id                     product_id
   ↓                                    ↓
거래상대방                              상품
```

## 검사 규칙과 오류 구성

각 도메인에는 실행 가능한 규칙 일곱 개를 두었다. 기본 식별자는 필수이고 수치에는 상·하한이 있으며 상태값은 정해진 목록에 있어야 한다. 시작일과 종료일의 순서를 비교하고 두 참조값이 각각 연결된 표에 존재하는지도 확인한다. 선택 입력 수치에는 별도의 범위 검사를 적용한다.

여기에 조건부 규칙 하나를 더했다. 예를 들어 “주문 상태가 발송 완료이면 운송장 번호가 필요하다”는 규칙이다. 현재 도구의 검사 유형으로는 이 조건을 충실하게 표현할 수 없어 초안으로 남겼다.

업무 데이터 200행 중 50행에는 오류나 누락을 의도적으로 넣었다. 아래 열 가지 유형을 각각 다섯 행에 적용했다.

| 유형 | 기대 판정 |
|---|---|
| 필수 식별자 누락 | 위반 |
| 수치 범위 초과 | 위반 |
| 목록에 없는 상태값 | 위반 |
| 시작일보다 이른 종료일 | 위반 |
| 첫 번째 참조 테이블에 없는 값 | 위반 |
| 두 번째 참조 테이블에 없는 값 | 위반 |
| 숫자로 읽을 수 없는 값 | 판단 불가 |
| 날짜로 읽을 수 없는 값 | 판단 불가 |
| 선택 입력 수치 누락 | 판단 불가 |
| 비교할 날짜 누락 | 판단 불가 |

정상 행에는 수치의 최솟값·최댓값과 두 날짜가 같은 경우도 포함했다. 경계값을 실수로 위반 처리하는지 확인하기 위해서다.

기대 판정 파일인 `expectations.json`은 이 오류 목록에서 직접 만들었다. 검사기를 실행한 결과를 정답으로 복사하지 않았으며 테스트에서는 총계뿐 아니라 모든 `(규칙 ID, 행 번호)`의 판정을 대조했다. 오류를 넣기 전의 정상 데이터도 따로 검사했다.

## 파일 형식별 검사 결과

네 도메인을 JSON·CSV·엑셀·SQLite로 읽어 총 16회 검사했다. **모든 규칙·행의 판정이 사전에 작성한 기대값과 일치했다.** 파일 형식 네 가지는 같은 데이터의 저장 방식만 바꾼 것이므로 독립적인 데이터셋 네 개로 세지 않는다.

| 도메인별 결과 | 건수 | 의미 |
|---|---:|---|
| 통과 | 1,350 | 적용한 규칙을 만족한 행별 검사 |
| 위반 | 30 | 여섯 가지 위반 유형 × 다섯 행 |
| 판단 불가 | 21 | 누락·형식 오류 20건과 미확정 규칙 안내 1건 |
| 합계 | 1,401 | 규칙 7개 × 200행 + 규칙 단위 안내 1건 |

**1,401건은 데이터 행 수가 아니라 검사 결과 수다.** 도메인마다 같은 오류 구성을 넣었기 때문에 위의 건수도 같다. 초안 상태인 조건부 규칙의 ‘판단 불가’는 실행을 보류했다는 뜻이며 조건부 규칙을 실제로 검증했다는 뜻이 아니다.

JSON으로 내보냈다가 다시 가져와도 행별 판정은 유지됐다. 정상 데이터 검사와 같은 파일을 다시 생성했을 때 바이트까지 같은지 확인하는 테스트를 포함해 관련 테스트 46개가 통과했다. 실제 브라우저에서도 네 프로젝트를 가져와 오류 없이 검사를 실행했다.

파일별 테이블 연결은 테스트 코드에서 명시했다. CSV 파일명, 엑셀의 `source.sheet`, SQLite의 `source.table`을 기존 테이블 ID와 연결한다. 자동 스키마 매칭 기능을 검증한 것은 아니다. 검토 중 엑셀의 화면 표시명과 실제 시트명이 다르다는 문제를 발견해 연결 코드를 고쳤고 데이터와 기대 판정은 바꾸지 않았다.

## LLM의 규칙 추출과 실행

네 도메인의 규칙 문서와 스키마를 `anthropic/claude-haiku-5.5`, `openai/gpt-6-luna`에 각각 전달했다. OpenRouter 호출은 총 8회이며 모두 완료됐다. 이번에 추가로 보고된 비용은 **$0.00769355**다. 문서 단위 생성 8회이지, 데이터 800행을 각각 질문한 실험은 아니다.

프롬프트에는 문서와 테이블·열 정보만 넣었다. 원본 데이터 행, 미리 작성한 참조 규칙, 기대 판정은 보내지 않았다.

각 응답은 실행 가능한 후보 일곱 개와 미지원 조건부 후보 한 개를 포함했다. 총 64개 제안 중 56개는 조정 역할의 에이전트가 원문 인용과 열 연결을 확인한 뒤 데모 실행용으로 확정했다. 조건 자체는 수정하지 않았고 나머지 조건부 후보 여덟 개는 초안으로 유지했다. 이 검토는 실제 사용자의 승인이나 별도 도메인 전문가 평가를 대신하지 않는다.

Haiku는 대소문자 구분, 날짜 형식, 누락값 처리 등에 확인 질문을 더 많이 남겼다. 질문과 검토 내용을 결과 파일에 보존했다. 검토한 LLM 규칙을 각 200행 데이터에 적용한 결과는 직접 작성한 규칙의 행별 판정과 같았다. 실패하거나 틀린 제안을 몰래 고쳐서 맞춘 결과는 아니다.

다만 이번 문서는 테이블명·열명·검사 조건을 명확하게 적었다. 모호한 PDF, 문맥에 숨어 있는 규칙, 임상 기록이나 법규 문서에서도 같은 결과가 나오는지는 확인하지 않았다. 원본 응답, 입력 해시, 후보 수와 검토 결정은 [실행 기록](../experiments/records/20261019-workbench-domain-demos.json)에 별도로 남겼다.

## 데이터 생성과 화면에서 확인하는 방법

저장소 루트에서 다음 명령을 실행하면 같은 데이터를 다시 만들고 검사할 수 있다. 두 출력 경로는 아직 없는 디렉터리여야 한다.

```bash
uv run --locked --group workbench python scripts/build_workbench_domain_demos.py --output _workspace/my-domain-data
uv run --locked --group workbench python scripts/check_workbench_domain_demos.py --data _workspace/my-domain-data --output _workspace/my-domain-results
```

도메인별 파일 구성은 다음과 같다.

```text
DOMAIN/
├── *.csv                  테이블별 CSV
├── data.xlsx              모든 테이블을 시트로 저장한 엑셀
├── data.sqlite            별도 DB 서버 없이 읽는 로컬 스냅샷
├── policy.md              데모용 규칙 문서
├── draft-project.json     모든 규칙이 검토 전인 작업 파일
├── confirmed-project.json 일곱 규칙을 데모용으로 확정한 작업 파일
├── baseline-project.json  오류를 넣기 전의 정상 데이터
├── expectations.json      기대 판정과 오류 삽입 내역
└── metadata.json          출처와 참고 자료, 사용 범위
```

화면에서 **프로젝트 JSON 가져오기**로 `confirmed-project.json`을 올리고 현재 작업을 교체한 뒤 **검사 결과**에서 실행하면 된다. 문서 추출부터 확인하려면 `draft-project.json`을 가져온다. 새 LLM 후보만 보고 싶다면 기존 초안 규칙을 지우고 `policy.md`를 선택해 LLM 제안을 요청한다. 생성된 후보 수 자체가 정확도는 아니며 지원하지 않거나 잘못 해석한 후보도 검토 대상으로 남겨야 한다.
