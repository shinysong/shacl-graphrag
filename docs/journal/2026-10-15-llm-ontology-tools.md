# 2026-10-15 — LLM 도구 선택과 조회 인터페이스

이번 실험에서 처음으로 LLM이 업무 질문을 읽고 SPARQL을 작성하며 도구를 선택하도록 연결했다. 이전 업무 실험에서는 정해진 규칙이 해석과 판단을 담당했다. 두 실행은 서로 다른 질문에 답한다.

## 조회와 검증의 선후관계

온톨로지 검증 도구가 있어도 모델이 해당 도구를 호출하지 않거나 근거를 가져오지 못하면 검증 효과를 측정하기 어렵다. 문자열 식별자를 URI로 바꾸어 조회한 경우처럼, 문법이 맞아도 결과가 비어 있을 수 있다. 빈 결과를 원천 데이터의 부재로 해석하면 조회 단계의 실패가 답변 단계의 보류로 바뀐다.

검증을 무조건 강제하는 방법도 있지만, 그것은 모델이 적절한 도구를 선택하는지 평가하는 실험과 다르다. 다음 설계에서는 도구 선택 능력과 검증 도구 자체의 유용성을 분리할 필요가 있다.

## 실험 입력의 품질

부품 영향 탐색의 공개 정책에 관계 방향 설명 오류가 있었다. 원천의 `part_of`는 부품에서 조립체로 향하므로 정방향으로, `contains`는 제품에서 조립체로 향하므로 역방향으로 탐색해야 한다. 그런데 정책 문장에는 `part_of`를 뒤집으라고 적었다.

실행 중 이 오류를 발견했다. 입력이나 정답을 중간에 고치지 않고 기록을 보존했다. 이 질문 유형의 결과는 모델 단독의 성능 차이로 해석할 수 없다. 나머지 유형을 따로 집계하더라도 사후 분리라는 점을 밝혀야 한다. 작성한 실험 정책과 실제 데이터의 일관성을 사전에 더 검토했어야 했다.

## 다음 비교의 우선순위

우선 공개 정책과 실제 레코드의 대응을 바로잡고 질의 인터페이스를 비교한다. 한 조건은 자유 SPARQL, 다른 조건은 모델이 관계 역할·대상·날짜·필터를 직접 고르는 구조화 조회다. 두 조건 모두 질문 해석을 모델에 맡기며 정답 업무 유형이나 결과를 자동으로 넣지 않는다.

이렇게 해야 “SPARQL 문자열을 잘 쓰는 능력”과 “어떤 관계를 조회해야 하는지 판단하는 능력”을 구분할 수 있다. 구조화 도구에도 잘못된 역할과 조건을 선택할 여지는 남겨야 한다. 모든 요청을 정답 템플릿으로 바꾸면 이전 규칙 기반 실험으로 돌아간다.

그다음 동일한 조회 조건에서 온톨로지 설명과 검증 도구를 비교한다. 검증 호출률, 잘못된 해석과 쿼리가 함께 통과한 사례, 근거 누락을 놓친 사례를 함께 살핀다. 같은 의미 정보를 JSON 설명으로 준 대조군도 있어야 온톨로지 표현 자체의 차이를 주장할 수 있다.
