# 쿼리 목록 6·24·72개 비교를 위한 실행기

쿼리 계약이 6개뿐인 비교에서는 전체 목록을 모델에 제공해도 부담이 작았다. 이전 두 모델 비교의 선택 결과도 같았다. 모델을 더 늘리기 전에 계약 목록이 커질 때 전체 목록 제공과 후보 검색의 차이를 확인할 실행기를 만들었다. 이번 작업은 구현과 오프라인 검증이다. 새 유료 호출은 0회다.

## 목록 크기와 공통 비교 대상

계약 목록은 6·24·72개로 구성했다. 기존 6개 공장 조회를 모든 크기에서 공통 비교 대상으로 유지하고, 나머지는 유지보수·교정·검사·문서 개정 등의 합성 기록 조회로 채웠다. 11개 기록 종류에 설비·주문 두 대상과 전체·현재 유효·만료 세 기간 조건을 조합한 66개 쿼리가 실제 SQLite에서 실행된다. 기존 6개 조회는 RDFLib을 사용한다.

같은 쿼리의 이름만 바꿔 개수를 늘리지는 않았다. 다만 같은 생성 틀에서 만든 기록 조회이므로 실제 기업의 다양한 쿼리 목록을 대표하지는 않는다. 이번 설계는 공통 대상 6개 주변에 다른 조회가 늘어나는 조건을 다룬다.

## 모델 선택과 검색 누락의 구분

전체 목록을 한 번 제공하는 조건과, 세부 요구마다 BM25 상위 3개를 제공하는 조건을 비교한다. 계약의 설명·입력·출력·지원 범위·한계는 두 조건에서 동일하게 유지했다. 검색 조건에서 나온 선택에는 입력 종류 검사를 추가로 적용하되, 같은 모델 응답을 재사용한다. 검사기가 다른 도구를 대신 골라주지는 않는다.

```text
질문과 계약 목록
  ├─ 전체 목록 ───────→ LLM 선택 → 고정 쿼리 실행
  └─ 검색 후보 3개 ───→ LLM 선택 → 고정 쿼리 실행
                           └─ 입력 종류 검사 → 고정 쿼리 실행
```

필요한 쿼리가 후보에 있었는지, 후보에 있는데도 모델이 잘못 골랐는지, 지원하지 않는 요구를 보류했는지를 따로 집계한다. 검사가 올바른 선택까지 막는 경우와 잘못된 선택을 통과시키는 경우도 남긴다. 일반 도구 호출도 입력 종류를 검사하므로, 검토 단계를 앞당긴 것만으로 실행 결과가 개선됐다고 해석하지 않는다.

## 개발 질문의 오프라인 결과

개발 질문 6건에는 세부 요구 12개가 있다. 이 중 10개는 제공된 조회로 처리할 수 있고, 2개는 납기나 문서 진위처럼 지원 서비스가 없다. 아래 수치는 모델 선택 결과가 아니라 필요한 쿼리가 후보에 포함됐는지를 센 것이다.

| 계약 수 | 전체 목록 후보 포함 | 검색 상위 3개 후보 포함 | 전체 목록 입력 바이트 합계 | 검색 입력 바이트 합계 |
| --- | --- | --- | ---: | ---: |
| 6 | 10/10 | 9/10 | 28,408 | 22,485 |
| 24 | 10/10 | 9/10 | 90,472 | 23,609 |
| 72 | 10/10 | 9/10 | 255,472 | 23,570 |

입력 바이트는 개발 질문 6건의 준비된 요청을 합친 값이다. 토큰 수나 실제 비용이 아니다. 이 개발 질문에서는 목록이 커져도 후보 포함률이 더 떨어지지 않았다. 전체 목록의 입력량은 커졌고 검색 입력량은 비슷했지만, 검색이 필요한 쿼리 하나를 놓친 점도 그대로다. LLM의 정확도·응답 시간·비용 차이는 아직 측정하지 않았다.

## 평가 질문과 호출 경계

개발 질문과 별도로 평가용 복합 질문 6건을 작성하고 해시를 고정했다. 준비 과정에서는 평가 질문의 검색 결과나 모델 선택 결과를 확인하지 않았다. 작성자가 문장과 의도 기준을 아는 합성 진단이며, 대표성 있는 미공개 벤치마크는 아니다. 질문 분해와 식별자 연결도 실험에서 미리 제공한다.

한 모델로 평가 질문 6건을 목록 크기 3개와 입력 조건 2개에 교차하면 최대 36회 호출이 필요하다. 저장된 후보 모델 가격으로 계산한 보수적 예약 합계는 3.0107340달러다. 실제 청구 예상액은 아니며, 호출 전 가격과 모델 지원 여부를 다시 확인해야 한다. 누적 5달러 원장과 실행 잠금은 준비 폴더를 바꿔도 공유한다. 현재 유료 실행은 잠겨 있다.

독립 검토에서 비용 집계 문제를 찾았다. 실패 호출의 비용이 전체 원장에는 남고 조건별 집계에는 빠질 수 있었다. 집계가 최종 원장 기록을 읽도록 수정했고, 실제 Gateway에 가짜 HTTP 응답을 넣어 비용이 알려진 실패와 미확정 실패를 각각 점검하는 테스트를 추가했다. 이는 실행기의 검증이며 제공자 동작이나 모델 품질을 입증하지 않는다.

## 다음 판단에 필요한 증거

다음 유료 비교에서는 검색이 입력량을 줄이면서도 필요한 후보를 유지하는지, 후보가 주어진 뒤 모델이 얼마나 잘 선택하는지 확인해야 한다. 전체 목록만으로 충분하거나 계약 검사에 추가 효과가 없어도 그 결과를 받아들인다. 이번 실행기는 그 차이를 기록하도록 만들었으며, 최종 답변의 개선 효과와 자율적인 질문 분해는 아직 평가 범위 밖이다.
